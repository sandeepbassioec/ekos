Concept 1.1, File 1: CacheLineConstants.cs
The Physics
This file defines hardware constants — numbers that come from the physical silicon of your CPU, not from any software decision. These numbers are the same on every modern x86-64 processor (Intel and AMD) since ~2004.

Constant 1: Cache Line Size = 64 bytes

Why 64? Because Intel and AMD designed their L1/L2/L3 caches to transfer data in 64-byte blocks. This is baked into the silicon — you can't change it, configure it, or override it. It's like the speed of light for your CPU's memory system.

When your code reads int x = myStruct.FieldA, the CPU doesn't fetch just those 4 bytes. It fetches the entire 64-byte block that contains those bytes. So if your struct is 64 bytes, ONE fetch gives you the ENTIRE struct.

Constant 2: Large Page Size = 2MB (2,097,152 bytes)

Normal memory pages are 4KB. The CPU has a small lookup table (TLB, ~64 entries) to translate virtual addresses to physical addresses. With 4KB pages, 64 entries cover only 256KB of memory. Your MemoryArena will be gigabytes — that means constant TLB misses (~10-30 ns each).

With 2MB pages: 64 TLB entries × 2MB = 128MB coverage. With 1GB pages: 64 entries × 1GB = 64GB. Your entire dataset fits in the TLB.

        // This is a hardware constant — not a software choice.
        Assert.Equal(64, CacheLineConstants.CacheLineSize);
    }

    [Fact]
    public void CacheLineSize_IsPowerOfTwo()
    {
        // WHY: Cache lines must be power-of-2 for bitwise alignment tricks.
        // Example: (address & ~63) gives the cache-line-aligned address.
        // If it's not power-of-2, this bitwise trick breaks.
        int size = CacheLineConstants.CacheLineSize;
        Assert.True(size > 0 && (size & (size - 1)) == 0,
            $"CacheLineSize {size} is not a power of two");
    }

    [Fact]
    public void LargePageSize_Is2MB()
    {

        // 2MB is the sweet spot — universally supported and 512x fewer TLB entries than 4KB.
        Assert.Equal(2 * 1024 * 1024, CacheLineConstants.LargePageSize);
    }

    [Fact]
    public void LargePageSize_IsMultipleOfCacheLine()
    {
        // WHY: A large page must contain a whole number of cache lines.
        // If it doesn't, the last cache line would span two pages — causing a page fault
        // in the middle of a cache line fetch. That would be catastrophic for performance.
        Assert.Equal(0, CacheLineConstants.LargePageSize % CacheLineConstants.CacheLineSize);
    }

namespace VectorVolt.Core.HAL;

/// <summary>
/// Hardware constants derived from the physical properties of modern x86-64 CPUs.
///
/// THE PHYSICS:
/// - CPU caches transfer data in fixed 64-byte blocks called "cache lines"
/// - The TLB (Translation Lookaside Buffer) maps virtual → physical pages
/// - Larger pages = fewer TLB entries needed = fewer expensive page walks
///
/// These constants are NOT configurable — they come from silicon specifications.
/// Intel and AMD have used these values since ~2004 (Pentium 4 / Athlon 64).
/// </summary>
public static class CacheLineConstants
{
    /// <summary>
    /// The size in bytes of one CPU cache line on all modern x86-64 processors.
    ///
    /// PHYSICS: When the CPU reads any byte from RAM, it fetches the entire
    /// 64-byte block containing that byte into L1 cache. This means:
    /// - A 64-byte struct = 1 cache fetch (optimal)
    /// - A 65-byte struct = 2 cache fetches (2x the latency)
    /// - A 40-byte struct = 1 fetch but wastes 24 bytes of bandwidth
    /// </summary>
    public const int CacheLineSize = 64;

    /// <summary>
    /// Large Page (HugePage) size: 2MB.
    ///
    /// PHYSICS: The CPU's TLB has ~64 entries to cache virtual→physical translations.
    /// - With 4KB pages:  64 × 4KB  = 256KB  covered (tiny — constant TLB misses)
    /// - With 2MB pages:  64 × 2MB  = 128MB  covered (good — fits working set)
    /// - With 1GB pages:  64 × 1GB  = 64GB   covered (entire dataset)
    ///
    /// Each TLB miss costs ~10-30 ns — at millions of ops/sec, this adds up fast.
    /// 2MB is the default HugePage size because it's universally supported on all
    /// x86-64 CPUs and operating systems (Linux, Windows).
    /// </summary>
    public const int LargePageSize = 2 * 1024 * 1024;
}

Concept 1.1, File 2: CommandFrame.cs
The Physics
This is the most important struct in all of VectorVolt. Every single command from every client enters the engine inside this struct. It's the "packet" of your system — like an IP packet is to networking, CommandFrame is to VectorVolt.

Why exactly 64 bytes?

Remember — the CPU fetches data in 64-byte cache lines. When the ShardExecutor processes commands at millions per second, each command must be:

One cache line — so one fetch gets the entire command (~1 ns from L1)
No GC — pure value type (struct), lives on stack or in unmanaged memory
Fixed layout — we control every byte's position, not the .NET runtime
The design challenge: fitting everything in 64 bytes

A command needs: who sent it (TenantId), what to do (CommandType), on which entity (AggregateId), ordering (SequenceNumber), timing (Timestamp), integrity (Checksum), and more. That's a lot of information to pack into 64 bytes.

The trick: variable-length data (the actual payload) lives OUTSIDE the struct. The CommandFrame only stores a PayloadOffset and PayloadLength — a pointer into the MemoryArena where the real data lives. This keeps the frame fixed-size.

Think of it like a postal envelope:

Envelope (CommandFrame, 64 bytes) = To, From, Date, Type, Tracking Number
Package (MemoryArena payload) = The actual goods inside
The envelope is always the same size. The package varies.

Key C# concepts you need:

struct — a value type. Lives on the stack or inline in arrays. No heap, no GC.
[StructLayout(LayoutKind.Explicit, Size = 64)] — tells the .NET runtime: "Don't rearrange my fields. I decide exactly where each byte goes, and the total size is 64."
[FieldOffset(N)] — places a field at exact byte offset N. This is how we pack fields like a puzzle.
Memory Map — study this carefully:

Byte 0                                                          Byte 63
┌────────┬────────┬────┬──┬─┬─┬──────────────────┬────┬────┬────────┬────┬────┐
│SeqNum  │Timestamp│Tid │Sh│T│F│   AggregateId    │PLen│POff│CorrId  │CRC │Rsv │
│ 8B     │ 8B     │ 4B │2B│1│1│     16B (Guid)   │ 4B │ 4B │ 8B     │ 4B │ 4B │
└────────┴────────┴────┴──┴─┴─┴──────────────────┴────┴────┴────────┴────┴────┘
Offset: 0    8       16   20 22 23 24              40   44   48       56   60

Every field is placed so that:

8-byte fields start at offsets divisible by 8 (0, 8, 48)
4-byte fields start at offsets divisible by 4 (16, 40, 44, 56, 60)
16-byte Guid starts at offset 24 (divisible by 8, good enough for SIMD)
Total = exactly 64 bytes, zero waste

using System.Runtime.CompilerServices;
using System.Runtime.InteropServices;

namespace VectorVolt.Core.HAL;

/// <summary>
/// The fundamental unit of work in VectorVolt. Every command from every client
/// enters the engine inside this 64-byte struct.
///
/// THE PHYSICS:
/// The CPU fetches data in 64-byte cache lines. This struct is exactly 64 bytes,
/// so ONE cache fetch loads the ENTIRE command. At millions of commands/sec,
/// this is the difference between microsecond and millisecond totals.
///
/// THE DESIGN:
/// Fixed-size header (this struct) + variable-size payload (in MemoryArena).
/// Like a postal envelope: the envelope is always 64 bytes, the package varies.
///
/// MEMORY MAP:
/// ┌────────┬────────┬────┬──┬─┬─┬────────────────┬────┬────┬────────┬────┬────┐
/// │SeqNum  │Timestmp│Tid │Sh│T│F│  AggregateId   │PLen│POff│CorrId  │CRC │Rsv │
/// │ 8B     │ 8B     │ 4B │2B│1│1│    16B Guid    │ 4B │ 4B │ 8B     │ 4B │ 4B │
/// └────────┴────────┴────┴──┴─┴─┴────────────────┴────┴────┴────────┴────┴────┘
/// Offset:0   8       16   20 22 23 24             40   44   48       56   60
/// Total: 64 bytes = 1 cache line. Zero waste. Zero GC.
/// </summary>
[StructLayout(LayoutKind.Explicit, Size = CacheLineConstants.CacheLineSize)]
public struct CommandFrame
{
    /// <summary>
    /// Monotonically increasing sequence number assigned by the ShardExecutor.
    /// This is the TOTAL ORDER — the source of determinism in the entire system.
    /// Every command gets a unique, ever-increasing number. During recovery,
    /// we replay commands in this order to rebuild state identically.
    /// Offset: 0 | Size: 8 bytes (long)
    /// </summary>
    [FieldOffset(0)]
    public long SequenceNumber;

    /// <summary>
    /// Engine-assigned timestamp in UTC ticks (100-nanosecond precision).
    /// NOT the client's wall clock — the engine assigns this to guarantee
    /// consistent ordering across all replicas.
    /// Offset: 8 | Size: 8 bytes (long)
    /// </summary>
    [FieldOffset(8)]
    public long Timestamp;

    /// <summary>
    /// Multi-tenant isolation key. Every piece of data in VectorVolt is scoped
    /// to a tenant. This is checked FIRST by the PolicyEngine — before any
    /// business logic runs.
    /// Offset: 16 | Size: 4 bytes (int) — supports ~2 billion tenants
    /// </summary>
    [FieldOffset(16)]
    public int TenantId;

    /// <summary>
    /// Target shard, determined by consistent hashing on AggregateId.
    /// Offset: 20 | Size: 2 bytes (short) — supports 32,767 shards
    /// </summary>
    [FieldOffset(20)]
    public short ShardId;

    /// <summary>
    /// Operation code: Create=1, Update=2, Delete=3, etc.
    /// Offset: 22 | Size: 1 byte — supports 256 command types
    /// </summary>
    [FieldOffset(22)]
    public byte CommandType;

    /// <summary>
    /// Bitflags for command metadata:
    /// Bit 0: High priority (QoS — processed before normal commands)
    /// Bit 1: Requires immediate fsync (don't batch, flush WAL now)
    /// Bit 2-7: Reserved for future use
    /// Offset: 23 | Size: 1 byte
    /// </summary>
    [FieldOffset(23)]
    public byte Flags;

    /// <summary>
    /// 128-bit unique identifier for the target entity/aggregate.
    /// Using Guid gives globally unique IDs without coordination between nodes.
    /// Offset: 24 (divisible by 8 — good SIMD alignment) | Size: 16 bytes
    /// </summary>
    [FieldOffset(24)]
    public Guid AggregateId;

    /// <summary>
    /// Length of the variable-size payload stored in MemoryArena.
    /// The actual payload data is NOT in this struct — that would blow
    /// the 64-byte budget. We store only a pointer (offset + length).
    /// Offset: 40 | Size: 4 bytes — supports payloads up to ~2 GB
    /// </summary>
    [FieldOffset(40)]
    public int PayloadLength;

    /// <summary>
    /// Byte offset into the MemoryArena where the payload begins.
    /// Arena stores the actual command data (serialized entity, etc).
    /// Offset: 44 | Size: 4 bytes
    /// </summary>
    [FieldOffset(44)]
    public int PayloadOffset;

    /// <summary>
    /// Distributed tracing ID. Tracks a command from client SDK →
    /// engine → WAL → projections. Essential for debugging in production.
    /// Offset: 48 | Size: 8 bytes (long)
    /// </summary>
    [FieldOffset(48)]
    public long CorrelationId;

    /// <summary>
    /// CRC32 checksum of the frame contents for integrity verification.
    /// Computed before WAL write, verified on WAL replay during recovery.
    /// Uses hardware-accelerated Sse42.Crc32 (~1 cycle per 8 bytes).
    /// Offset: 56 | Size: 4 bytes (uint)
    /// </summary>
    [FieldOffset(56)]
    public uint Checksum;

    /// <summary>
    /// Reserved padding to fill exactly 64 bytes.
    /// Available for future fields without breaking the cache line alignment.
    /// Offset: 60 | Size: 4 bytes (uint)
    /// </summary>
    [FieldOffset(60)]
    public uint Reserved;
}

✅ It's a value type (no GC)

Concept 1.1, File 3: WalRecord.cs
The Physics
Every command that enters VectorVolt through a CommandFrame gets processed, and once committed, it must be durably recorded to disk. That's the WalRecord — the "receipt" that proves a command was committed.

Why do we need a separate struct from CommandFrame?

CommandFrame is the input — what the client sent. WalRecord is the output — what the engine committed. They carry different information:

CommandFrame (input)	WalRecord (output)
CorrelationId (tracing)	SegmentId (which WAL file)
—	Epoch (leader election fencing)
Checksum + Reserved	Checksum + PrevChecksum (hash chain)
The most important difference is PrevChecksum — this creates a hash chain. Every WalRecord stores the checksum of the PREVIOUS record. This means:

Record 1: Checksum=0xAA, PrevChecksum=0x00 (first record)
Record 2: Checksum=0xBB, PrevChecksum=0xAA ← points back to Record 1
Record 3: Checksum=0xCC, PrevChecksum=0xBB ← points back to Record 2

If power fails mid-write and Record 2 gets corrupted, then Record 3's PrevChecksum won't match Record 2's Checksum. The chain breaks — and we know exactly where to truncate during recovery. This is the same principle behind blockchain, but we invented it decades before Bitcoin (it's called a Merkle chain).

Same 64-byte rule applies — one WalRecord = one cache line, because:

During in-memory batching (before flush), we iterate through records sequentially
On NVMe, 64 bytes pack perfectly: 64 records per 4KB page, zero fragmentation

/// The on-disk receipt of every committed command in VectorVolt's Write-Ahead Log.
///
/// THE PHYSICS:
/// NVMe drives achieve peak throughput with sequential, aligned writes.
/// At 64 bytes, exactly 64 WalRecords pack into one 4KB NVMe page — zero waste.
/// During in-memory batching (before flush), each record is one cache line fetch.
///
/// THE HASH CHAIN:
/// PrevChecksum links each record to the previous one. If power fails mid-write
/// and a record gets corrupted, the chain breaks at exactly that point.
/// During recovery, we walk the chain forward and truncate at the first break.
/// Same principle as blockchain — but invented decades earlier (Merkle chain).
///
/// MEMORY MAP:
/// ┌────────┬────────┬────┬──┬─┬─┬────────────────┬────┬────┬────┬────┬────┬────┐
/// │SeqNum  │Timestmp│Tid │Sh│R│F│  AggregateId   │PLen│POff│Seg │Epo │CRC │Prev│
/// │ 8B     │ 8B     │ 4B │2B│1│1│    16B Guid    │ 4B │ 4B │ 4B │ 4B │ 4B │ 4B │
/// └────────┴────────┴────┴──┴─┴─┴────────────────┴────┴────┴────┴────┴────┴────┘
/// Offset:0   8       16   20 22 23 24             40   44   48   52   56   60
/// Total: 64 bytes = 1 cache line = 1/64th of a 4KB NVMe page.
/// </summary>
[StructLayout(LayoutKind.Explicit, Size = CacheLineConstants.CacheLineSize)]
public struct WalRecord
{
    /// <summary>
    /// Links back to the CommandFrame that produced this record.
    /// Same monotonic sequence — the source of deterministic replay.
    /// Offset: 0 | Size: 8 bytes
    /// </summary>
    [FieldOffset(0)]
    public long SequenceNumber;

    /// <summary>
    /// Commit timestamp in UTC ticks. This is when the engine committed
    /// the command, not when the client sent it.
    /// Offset: 8 | Size: 8 bytes
    /// </summary>
    [FieldOffset(8)]
    public long Timestamp;

    /// <summary>
    /// Tenant isolation key — scopes this record to one tenant.
    /// Offset: 16 | Size: 4 bytes
    /// </summary>
    [FieldOffset(16)]
    public int TenantId;

    /// <summary>
    /// The shard that processed and committed this command.
    /// Offset: 20 | Size: 2 bytes
    /// </summary>
    [FieldOffset(20)]
    public short ShardId;

    /// <summary>
    /// Distinguishes record types in the WAL:
    ///   0 = Command (normal committed transaction)
    ///   1 = Snapshot marker (snapshot taken at this LSN)
    ///   2 = Epoch fence (leader change — prevents split-brain replay)
    /// Offset: 22 | Size: 1 byte
    /// </summary>
    [FieldOffset(22)]
    public byte RecordType;

    /// <summary>
    /// Bitflags for WAL record metadata.
    /// Offset: 23 | Size: 1 byte
    /// </summary>
    [FieldOffset(23)]
    public byte Flags;

    /// <summary>
    /// The entity this record applies to.
    /// Offset: 24 | Size: 16 bytes
    /// </summary>
    [FieldOffset(24)]
    public Guid AggregateId;

    /// <summary>
    /// Size of the serialized event payload in the WAL segment file.
    /// Offset: 40 | Size: 4 bytes
    /// </summary>
    [FieldOffset(40)]
    public int PayloadLength;

    /// <summary>
    /// Byte offset within the WAL segment file where the payload begins.
    /// The payload is written sequentially after the header batch.
    /// Offset: 44 | Size: 4 bytes
    /// </summary>
    [FieldOffset(44)]
    public int PayloadOffset;

    /// <summary>
    /// Which WAL segment file contains this record's payload.
    /// WAL is split into fixed-size segments (256MB each) for manageability.
    /// Offset: 48 | Size: 4 bytes
    /// </summary>
    [FieldOffset(48)]
    public int SegmentId;

    /// <summary>
    /// Leader election epoch. During recovery, records from a stale leader
    /// (lower epoch) are discarded. This prevents split-brain data corruption.
    /// Offset: 52 | Size: 4 bytes
    /// </summary>
    [FieldOffset(52)]
    public int Epoch;

    /// <summary>
    /// CRC32 checksum of THIS record's contents.
    /// Offset: 56 | Size: 4 bytes
    /// </summary>
    [FieldOffset(56)]
    public uint Checksum;

    /// <summary>
    /// CRC32 checksum of the PREVIOUS record — creates the hash chain.
    /// If power fails mid-write, the chain break tells us exactly
    /// where to truncate. Walk forward, stop at first mismatch.
    /// Offset: 60 | Size: 4 bytes
    /// </summary>
    [FieldOffset(60)]
    public uint PrevChecksum;
}

Concept 1.2: MemoryArena — The Zero-GC Bump Allocator
The Physics First
Every time you write new object() in C#, the .NET runtime allocates memory on the managed heap. The Garbage Collector (GC) tracks every allocation, and periodically pauses ALL threads to scan and reclaim dead objects. These pauses range from microseconds to milliseconds.

For a normal web app, that's fine. For VectorVolt processing millions of commands per second at 20 ns each, a single GC pause of 1 ms = 50,000 lost commands.

The solution: never use the managed heap on the hot path.

Instead, we allocate a giant block of unmanaged memory at startup using NativeMemory.AlignedAlloc. The GC doesn't know this memory exists — it can't pause us to scan it, because there's nothing to scan.

How a Bump Allocator Works
Traditional allocators (malloc, new) are complex — they maintain free lists, handle fragmentation, merge adjacent free blocks. That complexity costs ~50-100 ns per allocation.

A bump allocator is the simplest possible allocator:

Arena (1 MB of unmanaged memory):
┌──────────────────────────────────────────────────────────┐
│ Used ██████████████░░░░░░░░░░░░░░░░░░░░░░░░░░ Free      │
└──────────────────────────────────────────────────────────┘
                      ↑
                   _offset (just a number)

Allocate 64 bytes:
  1. old_offset = _offset           (read one integer)
  2. _offset = old_offset + 64      (add one integer)
  3. return pointer to old_offset   (done!)

That's it. THREE operations. ~1-2 ns.

Reset (free all memory):

  _offset = 0;    // ONE operation. All memory reclaimed instantly.

No free lists. No fragmentation. No scanning. Just increment a number to allocate, zero it to free everything.

Why this works for VectorVolt:

The ShardExecutor processes commands in cycles. Each cycle:

Read batch of commands from ring buffer
Process them (allocating temp data from the arena)
Write results to WAL
Reset the arena — all temp data is gone, ready for next cycle
We never need to free individual allocations — we always free EVERYTHING at once. That's what makes a bump allocator perfect.

Cache-Line Alignment
Every allocation from the arena must be aligned to 64 bytes (cache line boundary). Why?

UNALIGNED allocation (40 bytes at offset 50):
Cache Line 0: [........██████████]  ← bytes 50-63 (14 bytes)
Cache Line 1: [██████████████....]  ← bytes 64-89 (26 bytes)
               ↑ TWO cache fetches to read 40 bytes!

ALIGNED allocation (64 bytes at offset 64):
Cache Line 1: [████████████████████████████████]  ← bytes 64-127 (all 64)
               ↑ ONE cache fetch. Perfect.

The alignment formula:

aligned_size = (requested_size + 63) & ~63

This rounds UP to the next multiple of 64. Examples:

40 bytes → 64 bytes (wastes 24 bytes, but saves a cache miss worth ~100 ns)
64 bytes → 64 bytes (perfect fit)
100 bytes → 128 bytes (2 cache lines)
The wasted bytes are worth it — one cache miss saved = ~100 ns saved.

using System.Runtime.InteropServices;

namespace VectorVolt.Core.HAL;

/// <summary>
/// Zero-GC bump allocator using unmanaged memory.
///
/// THE PHYSICS:
/// .NET's GC pauses ALL threads to scan the managed heap. At 1M+ ops/sec,
/// even a 1 ms pause = 50,000 lost commands. Solution: never use the managed heap.
///
/// HOW IT WORKS:
/// 1. At startup, allocate a big block of unmanaged memory (NativeMemory.AlignedAlloc)
/// 2. The GC doesn't know this memory exists — it can't pause us to scan it
/// 3. To allocate: increment _offset (one addition, ~1 ns)
/// 4. To free everything: set _offset = 0 (one assignment, ~1 ns)
///
/// WHY BUMP ALLOCATOR:
/// Traditional allocators (malloc) maintain free lists, handle fragmentation,
/// merge blocks — ~50-100 ns per allocation. We just bump a pointer: ~1-2 ns.
/// We can do this because the ShardExecutor frees EVERYTHING at once after each
/// command cycle — we never need to free individual allocations.
///
/// ALIGNMENT:
/// Every allocation is rounded up to 64 bytes (cache line boundary).
/// This guarantees no struct ever spans two cache lines.
///
/// LIFECYCLE:
/// Created once at shard startup → used for millions of cycles → disposed at shutdown.
/// Each cycle: Allocate → Process → Reset → Repeat.
/// </summary>
public sealed class MemoryArena : IDisposable
{
    private readonly unsafe byte* _buffer;  // Start of unmanaged memory block
    private readonly int _capacity;          // Total size in bytes (cache-line aligned)
    private int _offset;                     // Current allocation position (the "bump pointer")
    private bool _disposed;                  // Prevent double-free

    /// <summary>
    /// Creates a new MemoryArena with the specified capacity.
    ///
    /// THE PHYSICS:
    /// NativeMemory.AlignedAlloc allocates memory that:
    /// - Is invisible to the .NET GC (zero GC pressure)
    /// - Is aligned to the specified boundary (cache line = 64 bytes)
    /// - Must be manually freed (we do this in Dispose)
    /// </summary>
    /// <param name="capacityBytes">
    /// Requested capacity in bytes. Will be rounded UP to the next
    /// cache line boundary. Example: 100 → 128 bytes.
    /// </param>
    public unsafe MemoryArena(int capacityBytes)
    {
        if (capacityBytes <= 0)
            throw new ArgumentException("Capacity must be positive", nameof(capacityBytes));

        // Round up to cache line boundary: (size + 63) & ~63
        // Example: 100 + 63 = 163 → 163 & ~63 = 163 & 0xFFFFFFC0 = 128
        _capacity = AlignToCacheLine(capacityBytes);

        // Allocate unmanaged memory, aligned to cache line boundary.
        // This memory is INVISIBLE to the GC — zero scanning, zero pauses.
        _buffer = (byte*)NativeMemory.AlignedAlloc(
            byteCount: (nuint)_capacity,
            alignment: (nuint)CacheLineConstants.CacheLineSize
        );

        _offset = 0;
    }

    /// <summary>
    /// How many bytes have been allocated from this arena.
    /// </summary>
    public int UsedBytes => _offset;

    /// <summary>
    /// Total capacity in bytes (cache-line aligned).
    /// </summary>
    public int Capacity => _capacity;

    /// <summary>
    /// Allocate a block of memory from the arena, aligned to cache line boundary.
    ///
    /// HOW IT WORKS (3 steps, ~1-2 ns):
    /// 1. Round requested size up to next 64-byte boundary
    /// 2. Check if we have enough space
    /// 3. Bump the offset pointer and return the old position
    ///
    /// COST: One addition + one comparison. No locks, no free lists, no GC.
    /// </summary>
    /// <param name="sizeBytes">Number of bytes needed. Will be rounded up to 64.</param>
    /// <returns>Pointer to the allocated memory block.</returns>
    public unsafe byte* Allocate(int sizeBytes)
    {
        if (sizeBytes <= 0)
            throw new ArgumentException("Size must be positive", nameof(sizeBytes));

        // Round up to cache line boundary
        int alignedSize = AlignToCacheLine(sizeBytes);

        // Check capacity
        int newOffset = _offset + alignedSize;
        if (newOffset > _capacity)
            throw new OutOfMemoryException(
                $"MemoryArena exhausted: requested {alignedSize} bytes, " +
                $"but only {_capacity - _offset} of {_capacity} bytes remaining");

        // Bump the pointer — this IS the allocation
        byte* ptr = _buffer + _offset;
        _offset = newOffset;

        return ptr;
    }

    /// <summary>
    /// Reclaim ALL memory instantly by resetting the offset to zero.
    ///
    /// THE PHYSICS:
    /// Traditional free: walk free list, merge blocks, update metadata → ~50-100 ns
    /// Our reset: _offset = 0 → ~1 ns. One instruction. All memory reclaimed.
    ///
    /// Called by ShardExecutor after every command batch cycle.
    /// </summary>
    public void Reset()
    {
        _offset = 0;
    }

    /// <summary>
    /// Rounds a size up to the next cache line boundary (multiple of 64).
    ///
    /// THE MATH: (size + 63) &amp; ~63
    /// - Adding 63 ensures any non-multiple rounds up
    /// - Bitwise AND with ~63 (0xFFFFFFC0) clears the low 6 bits
    /// - This is branchless — no if/else, just two CPU instructions
    ///
    /// Examples: 1→64, 40→64, 64→64, 65→128, 100→128
    /// </summary>
    internal static int AlignToCacheLine(int size)
    {
        return (size + (CacheLineConstants.CacheLineSize - 1))
             & ~(CacheLineConstants.CacheLineSize - 1);
    }

    /// <summary>
    /// Frees the unmanaged memory block.
    ///
    /// CRITICAL: Because this memory is invisible to the GC, if we don't call
    /// Dispose, the memory leaks FOREVER. The GC will never reclaim it.
    /// Always use MemoryArena in a 'using' statement or call Dispose explicitly.
    /// </summary>
    public unsafe void Dispose()
    {
        if (!_disposed)
        {
            NativeMemory.AlignedFree(_buffer);
            _disposed = true;
        }
    }
}
