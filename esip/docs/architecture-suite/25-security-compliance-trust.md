## 1. SEC-SSE — Server-Side Enforcement Mandate

> **Design principle:** The React client is presentation-only. Every authorization decision, every business-logic rule, every secret, every sensitive data access, and every mutating operation SHALL be enforced in the .NET Core 10 API layer behind the DAL/ports abstraction. The current state (business logic embedded in React pages talking directly to Firebase) is a security debt that SHALL be systematically migrated. No new feature introduced after this volume is ratified may embed security-relevant logic client-side.

### 1.1 Migration Mandate: Client-Embedded Logic → Server-Side API

| ID | Title | SHALL Description | Category | Persona(s) | Priority | Rationale/Source |
|----|-------|-------------------|----------|------------|----------|-----------------|
| REQ-SEC-001 | Server-Side Enforcement Mandate | The platform SHALL enforce all authorization decisions, business rules, and data-access constraints exclusively in the .NET Core 10 server-side API; the React client SHALL be treated as an untrusted, presentation-only consumer and SHALL never receive authorization grants, secret values, or rule-engine outcomes directly from Firebase or any other backend-as-a-service callable from the browser bundle. | Security | All | Must | OWASP API Security Top 10 API2 (Broken Object-Level Authorization), API5 (Broken Function-Level Authorization); direct BaaS calls from the client bypass all server-side controls |
| REQ-SEC-002 | Firebase Direct-Call Migration Plan | The platform SHALL maintain and execute a documented migration plan that enumerates every Firebase direct call currently in the React codebase (Firestore reads/writes, Firebase Storage uploads, Firebase Auth operations that carry business logic), assigns each a migration ticket, and tracks completion; no new direct-Firebase business-logic calls SHALL be introduced post-ratification. | Security | Admin | Must | The current architecture is a known security concern (per TECH-STACK.md); migration must be tracked, not assumed |
| REQ-SEC-003 | Client Is Presentation-Only | The .NET API SHALL validate and authorize every request independently of what the client claims; the client SHALL NOT be trusted to enforce RBAC, ABAC, tenant scoping, record-level permissions, or feature-flag entitlements; all such checks SHALL be re-evaluated on the server for every request. | Security | All | Must | Defense-in-depth; client-side enforcement is always bypassable by a modified browser client or direct API call |
| REQ-SEC-004 | No Security-Relevant Secrets in Browser Bundle | The platform SHALL ensure that no API keys, signing secrets, service-account credentials, AI provider keys, database connection strings, or cryptographic material are included in the compiled JavaScript bundle served to the browser; all such material SHALL reside exclusively in the server-side secrets vault and be accessed via the .NET API only. | Security | Admin | Must | Secrets in browser bundles are trivially exfiltrated; this explicitly covers the `ai-proxy` key (AWS Bedrock / Azure OpenAI / etc.) referenced in TECH-STACK.md |
| REQ-SEC-005 | No Security-Relevant Rules in Browser Bundle | The platform SHALL ensure that feature-flag logic, RBAC role definitions, ABAC policy expressions, data-classification rules, and retention/DLP policies are NOT embedded in the client bundle; they SHALL be evaluated server-side and their results communicated to the client only as entitlement tokens or UI-capability flags. | Security | All | Must | Any rule in the browser is a rule that can be bypassed; hardened server-side enforcement is the only reliable control |
| REQ-SEC-006 | API Gateway as the Single Entry Point | All client traffic to backend resources (database, object storage, AI proxy, connector credentials) SHALL flow through the .NET API gateway; direct browser-to-storage, browser-to-AI-provider, and browser-to-database calls SHALL be blocked at the network/CORS layer; the API gateway is the sole enforcement point for auth, rate-limiting, audit, and input validation. | Security | All | Must | OWASP API Top 10 API8 (Security Misconfiguration); centralizing enforcement eliminates gaps at each resource boundary |
| REQ-SEC-007 | Incremental Migration Verification | Each migrated feature area SHALL be verified via a security test that confirms: (a) the old direct-Firebase path is blocked or removed, (b) the new server-side path enforces authorization, and (c) no secret or rule previously in the client is reachable from the browser. Verification results SHALL be recorded in the migration tracking artifact. | Security | Admin | Must | Migration without verification is incomplete migration; regression risk is high in phased cutover |

### 1.2 Defense-in-Depth Architecture

| ID | Title | SHALL Description | Category | Persona(s) | Priority | Rationale/Source |
|----|-------|-------------------|----------|------------|----------|-----------------|
| REQ-SEC-008 | Layered Security Architecture | The platform SHALL implement security controls in layers: (a) network/perimeter (TLS, WAF, CORS, IP allowlist where configured), (b) API gateway (authentication, rate limiting, input validation, audit), (c) service layer (authorization, business-logic checks, ABAC), (d) data layer (row-level security, field-level encryption, tenant scoping), (e) storage layer (encrypted at rest, access-controlled buckets/volumes); no single layer SHALL be the only barrier for any sensitive operation. | Security | All | Must | Defense-in-depth principle; NIST SP 800-53 SC-7, AC-4 |
| REQ-SEC-009 | Principle of Least Privilege (Platform-Wide) | Every process, service account, database role, object-storage IAM role, and AI provider key SHALL be granted only the minimum permissions required for its specific function; no wildcard permissions, no shared service accounts across tenants, no persistent elevated privileges; privilege escalation SHALL require explicit, time-bounded, audited approval. | Security | Admin | Must | NIST SP 800-53 AC-6; CIS Control 6 |
| REQ-SEC-010 | Zero-Trust Internal Communication | All inter-service communication (React → .NET API, .NET API → Rust code-scan service, .NET API → database, .NET API → object storage, .NET API → AI proxy) SHALL use mutual TLS or service-mesh-level identity attestation; no service SHALL accept traffic from an unauthenticated caller, even inside the cluster. | Security | Admin | Must | Zero-trust network architecture (NIST SP 800-207); internal network compromise SHALL not grant unauthenticated service access |

## 2. SEC-API — API & Application Security

> **Design principle:** The .NET Core 10 API SHALL be hardened against every class of web/API attack catalogued in OWASP ASVS Level 2 as a baseline, with Level 3 controls applied to authentication, session management, cryptography, and data protection endpoints. Every endpoint is authorized, every input validated, every output encoded. OWASP API Security Top 10 2023 is the minimum mandatory checklist.

### 2.1 Authorization at Every Endpoint

| ID | Title | SHALL Description | Category | Persona(s) | Priority | Rationale/Source |
|----|-------|-------------------|----------|------------|----------|-----------------|
| REQ-SEC-011 | Authorization on Every Endpoint | Every API endpoint (REST or GraphQL) SHALL enforce an explicit authorization check; there SHALL be no endpoint that is implicitly public by default; unauthenticated access SHALL be explicitly declared and limited to login, health-check, and public-metadata endpoints only. | Security | All | Must | OWASP API2 (Broken Object-Level Authorization), API5 (Broken Function-Level Authorization); implicit public is the most common misconfiguration |
| REQ-SEC-012 | Object-Level Authorization (BOLA/IDOR Prevention) | Every data-retrieval and data-mutation API call SHALL verify that the authenticated caller has been explicitly granted access to the specific object (artifact, project, workspace, file, tenant) being operated on; object IDs in request parameters SHALL never be trusted without re-validation of ownership and tenant binding. | Security | All | Must | OWASP API1 (BOLA); also known as IDOR; cross-tenant data leakage is the most common enterprise API vulnerability |
| REQ-SEC-013 | Function-Level Authorization | Destructive or privileged operations (delete artifact, export all tenant data, change security policy, create admin user, trigger bulk operations) SHALL require a role check beyond basic authentication; role checks SHALL be evaluated server-side using the RBAC/ABAC engine (V11) with the caller's current session claims. | Security | Admin, Security-Admin | Must | OWASP API5; privilege escalation via undocumented admin endpoints is a critical risk |
| REQ-SEC-014 | RBAC/ABAC Enforcement via Server-Side Policy Engine | Authorization SHALL be evaluated by the centralized server-side policy engine (V11); policies SHALL be expressed as code-auditable rules (not ad-hoc if/else in controllers); the policy engine SHALL log every authorization decision for audit; authorization decisions SHALL be cacheable for performance but invalidated immediately on role/permission change. | Security | All | Must | NIST SP 800-53 AC-3; centralized policy avoids enforcement gaps across microservices |
| REQ-SEC-015 | Cross-Tenant Isolation at API Layer | Every authenticated request SHALL carry a validated tenant context (derived from the JWT/session, never from a client-supplied parameter alone); all database queries SHALL be automatically scoped to the caller's tenant by the repository layer; any query that could return cross-tenant data SHALL fail closed with a 403, not a data leak. | Security | All | Must | Multi-tenancy isolation; data residency compliance; GDPR Art. 5(f) integrity and confidentiality |

### 2.2 Input Validation & Output Encoding

| ID | Title | SHALL Description | Category | Persona(s) | Priority | Rationale/Source |
|----|-------|-------------------|----------|------------|----------|-----------------|
| REQ-SEC-016 | Server-Side Input Validation | Every API input (path parameters, query parameters, request body, HTTP headers used as inputs, multipart form fields) SHALL be validated server-side against a declared schema (type, format, length, allowed values, regex where applicable) before any business logic or storage operation is performed; validation errors SHALL return HTTP 400 with actionable, non-information-leaking error messages. | Security | All | Must | OWASP ASVS V5.1 (Input Validation); CWE-20; client-side validation is UI convenience, not security |
| REQ-SEC-017 | Output Encoding | All data returned in API responses that will be rendered in the browser SHALL be appropriately encoded to prevent XSS; string values that may contain HTML, JavaScript, or SVG SHALL be HTML-entity-encoded or sanitized using an allowlist-based HTML sanitizer before inclusion in any rendered output. | Security | All | Must | OWASP ASVS V5.3 (Output Encoding); CWE-79 (XSS) |
| REQ-SEC-018 | Parameterized Queries / ORM Enforcement | All database interactions SHALL use parameterized queries or ORM-generated SQL (EF Core); raw SQL string concatenation involving user-supplied data is prohibited; any native SQL queries (e.g., for performance-critical paths) SHALL be reviewed and approved in the secure code-review gate. | Security | All | Must | OWASP ASVS V5.3; CWE-89 (SQL Injection) |
| REQ-SEC-019 | Strict Content-Type Validation | The API SHALL reject requests whose declared `Content-Type` does not match the actual content; multipart uploads SHALL validate MIME type against actual file magic bytes, not the client-declared content-type header. | Security | All | Must | MIME confusion attacks; file-type bypass is a prerequisite for many upload-based exploits |
| REQ-SEC-020 | JSON Schema Validation for Structured Payloads | Complex structured payloads (artifact creation, template definitions, metamodel configuration, AI prompt packs) SHALL be validated against a declared JSON Schema before processing; overly large payloads (bomb payloads) SHALL be rejected by configurable maximum size limits per endpoint category. | Security | All | Must | CWE-400 (Uncontrolled Resource Consumption); protection against deeply nested JSON / billion-laughs-style attacks |

### 2.3 Anti-CSRF / XSS / SSRF / Injection

| ID | Title | SHALL Description | Category | Persona(s) | Priority | Rationale/Source |
|----|-------|-------------------|----------|------------|----------|-----------------|
| REQ-SEC-021 | CSRF Protection | The platform SHALL implement CSRF protection for all state-mutating operations using double-submit cookie or synchronizer token pattern (or rely on SameSite=Strict/Lax cookies + CORS policy where the API is an SPA-only backend); CSRF tokens SHALL be rotated per session and per form where applicable. | Security | All | Must | OWASP ASVS V4.2; CWE-352 |
| REQ-SEC-022 | XSS Prevention (Stored, Reflected, DOM) | The platform SHALL prevent stored, reflected, and DOM-based XSS through: (a) CSP (Content-Security-Policy) header with a restrictive allow-list (no `unsafe-inline` script), (b) server-side output encoding (REQ-SEC-017), (c) React's default JSX escaping supplemented by DOMPurify for rich-text fields that allow HTML, (d) prohibition of `eval()` and dynamic code execution in the client bundle. | Security | All | Must | OWASP ASVS V5.3; OWASP Top 10 A03:2021 |
| REQ-SEC-023 | SSRF Prevention | The platform SHALL prevent Server-Side Request Forgery: all outbound HTTP requests made by the .NET API on behalf of user-supplied URLs (e.g., connector webhook targets, import-from-URL, AI callback URLs) SHALL be validated against an allowlist of permitted domains and IP ranges; requests to RFC-1918 private ranges, loopback, link-local, and cloud metadata endpoints (169.254.169.254) SHALL be blocked and alerted; DNS rebinding SHALL be mitigated by resolving the hostname before the allowlist check. | Security | All | Must | OWASP API Top 10 2023 API7 (SSRF); CWE-918 |
| REQ-SEC-024 | Command Injection Prevention | The platform SHALL avoid shell command construction from user input; where the Rust code-scan service or .NET service invokes system processes (e.g., git, tree-sitter binaries), arguments SHALL be passed as structured arrays, not string-concatenated shell commands; shell metacharacters in inputs SHALL be rejected or escaped before any process invocation. | Security | All | Must | CWE-78 (OS Command Injection) |
| REQ-SEC-025 | Path Traversal Prevention | File path construction in the .NET API and Rust service SHALL canonicalize and validate all paths against a declared base directory before any file I/O; user-supplied path segments (filenames, directory names in Knowledge Hub connector paths) SHALL be sanitized to remove `../`, `..\\`, null bytes, and other traversal sequences. | Security | All | Must | CWE-22 (Path Traversal) |
| REQ-SEC-026 | XXE Prevention | XML parsing (e.g., Visio/drawio/XMI imports in V18, SAML assertions from IdP) SHALL disable external entity processing (XXE); XML parsers SHALL be configured with `FEATURE_SECURE_PROCESSING` equivalent settings; DTD processing SHALL be disabled. | Security | All | Must | CWE-611 (XXE); XML-based import formats are a common XXE vector |
| REQ-SEC-027 | Template Injection Prevention | AI prompt templates (V06) and document templates (V10/V23) that interpolate user-supplied values SHALL use a safe, context-aware interpolation engine that does not allow escape to template directives or code execution; Razor / Handlebars / similar templating in deliverable generation SHALL disable server-side-code execution via template injection. | Security | All | Must | CWE-94 (Code Injection via template); server-side template injection is critical severity |

### 2.4 Rate Limiting, Throttling & Abuse Prevention

| ID | Title | SHALL Description | Category | Persona(s) | Priority | Rationale/Source |
|----|-------|-------------------|----------|------------|----------|-----------------|
| REQ-SEC-028 | API Rate Limiting (Per-Tenant & Per-User) | The platform SHALL enforce configurable rate limits on all API endpoints at two levels: (a) per-authenticated-user (short-window: requests/minute, requests/hour), (b) per-tenant (aggregate: requests/minute, requests/day); rate-limit thresholds SHALL be configurable by platform operators and optionally by tenant admins within platform-set maximums; HTTP 429 responses SHALL include `Retry-After` headers. | Security | Admin | Must | OWASP API Top 10 2023 API4 (Unrestricted Resource Consumption); denial-of-service and credential-stuffing mitigation |
| REQ-SEC-029 | AI Endpoint Rate Limiting | AI-powered endpoints (extraction, generation, copilot, diagram AI, code analysis) SHALL have separate, tighter rate limits reflecting the higher per-call cost; per-user per-day token budgets SHALL be configurable in the admin console; budget exhaustion SHALL return a clear user-facing message, not a silent failure. | Security | Admin | Must | Cost protection (V06 §13); LLM abuse prevention; also cross-references REQ-SEC-028 |
| REQ-SEC-030 | Brute-Force & Credential-Stuffing Protection | Login, password-reset, MFA-verification, and API-key-activation endpoints SHALL implement exponential back-off and account lockout after configurable failed-attempt thresholds (default: 5 attempts → 15-minute lockout); lockout events SHALL be logged and optionally trigger an admin alert. | Security | All | Must | OWASP ASVS V2.2; CWE-307 |
| REQ-SEC-031 | Upload Rate Limiting | File-upload endpoints SHALL enforce per-user and per-tenant rate limits on both upload frequency (files/hour) and total upload volume (MB/hour/day); bulk-upload operations SHALL be queued and processed asynchronously with tenant-scoped concurrency limits to prevent storage-layer abuse. | Security | Admin | Must | Resource exhaustion protection; cost control; ties to REQ-SEC-070 (AV scan queue saturation) |
| REQ-SEC-032 | Bot / Automation Detection | The platform SHALL implement signals-based detection for automated abuse patterns (rapid sequential requests, identical payload enumeration, anomalous off-hours bursts) and SHALL support integration with a configurable WAF or bot-management service; detected automation patterns SHALL trigger alerts and optionally temporary IP- or account-level throttling, logged to the audit trail. | Security | Admin | Should | API scraping and credential stuffing are common SaaS attack vectors; detection complements rate limiting |

### 2.5 Security Headers & Secure Error Handling

| ID | Title | SHALL Description | Category | Persona(s) | Priority | Rationale/Source |
|----|-------|-------------------|----------|------------|----------|-----------------|
| REQ-SEC-033 | HTTP Security Headers | The platform SHALL emit the following security headers on all responses from the .NET API and the Vite/React static bundle: `Strict-Transport-Security` (max-age ≥ 31536000, includeSubDomains), `Content-Security-Policy` (restrictive, no `unsafe-eval`), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY` or `frame-ancestors 'none'`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` disabling camera/microphone/geolocation unless needed; headers SHALL be validated in CI via automated security-header-check tooling. | Security | All | Must | OWASP ASVS V14.4; securityheaders.com grade A baseline |
| REQ-SEC-034 | CORS Policy Enforcement | CORS policies SHALL explicitly enumerate allowed origins (no wildcard `*` in production); allowed origins SHALL be validated against the tenant's configured domain list maintained server-side; the `Access-Control-Allow-Origin` response header SHALL reflect only matching origins, never echoing back arbitrary caller-supplied `Origin` values. | Security | All | Must | OWASP ASVS V14.5; CORS misconfiguration is a frequent API vulnerability |
| REQ-SEC-035 | Secure Error Handling (No Information Leakage) | API error responses in production SHALL return generic messages to the client (e.g., "An error occurred — reference: [correlation-ID]") and SHALL NOT include stack traces, database error messages, internal class names, SQL fragments, file system paths, or internal service names; full error detail SHALL be logged server-side only, keyed by correlation ID; correlation IDs SHALL be logged with sufficient context to enable investigation without client disclosure. | Security | All | Must | OWASP ASVS V7.4; CWE-209 (Information Exposure Through Error Messages) |
| REQ-SEC-036 | Structured Logging Without PII Leak | Server-side logs SHALL be structured (JSON) and SHALL redact or hash sensitive field values (passwords, tokens, PII, full file content) before emission; a logging schema SHALL enumerate which fields are safe to log verbatim and which require redaction; log-forwarding pipelines (SIEM) SHALL receive only the redacted stream. | Security | Admin | Must | GDPR Art. 5(f); log exfiltration must not yield usable credentials or PII |

## 3. SEC-ENC — Encryption & Secrets Management

> **Design principle:** Data is encrypted in transit between every pair of communicating components, and at rest in every storage medium. Secrets never appear in source code, client bundles, environment variables in container images, or unencrypted configuration files. Customers who require it can manage their own encryption keys (BYOK).

### 3.1 Encryption in Transit

| ID | Title | SHALL Description | Category | Persona(s) | Priority | Rationale/Source |
|----|-------|-------------------|----------|------------|----------|-----------------|
| REQ-SEC-037 | TLS 1.2+ on All External Channels | All external-facing HTTP endpoints (API, static assets, WebSocket connections) SHALL be served exclusively over TLS 1.2 or TLS 1.3; TLS 1.0 and 1.1 SHALL be disabled; plaintext HTTP SHALL redirect to HTTPS with a 301 and HSTS enforced thereafter. | Security | All | Must | OWASP ASVS V9.1; NIST SP 800-52 Rev 2; PCI DSS 4.0 req 4.2.1; HIPAA §164.312(e)(1) |
| REQ-SEC-038 | TLS 1.3 Preferred | The platform SHALL configure TLS listeners to prefer TLS 1.3 where both sides support it; TLS 1.2 cipher suites SHALL be restricted to ECDHE+AES-GCM and ECDHE+CHACHA20 suites; RC4, 3DES, and MD5-based suites SHALL be disabled. | Security | All | Must | NIST SP 800-52 Rev 2 §3.3; weak cipher suite use enables downgrade and padding-oracle attacks |
| REQ-SEC-039 | mTLS for Internal Service-to-Service | All internal service-to-service communication (API ↔ Rust code-scan service, API ↔ AI proxy, API ↔ background workers) within the K8s cluster SHALL use mTLS via a service mesh (e.g., Istio/Linkerd) or explicit certificate-pinned client authentication; certificates SHALL be rotated automatically by the certificate manager. | Security | Admin | Must | Zero-trust internal network (REQ-SEC-010); prevents lateral movement after container compromise |
| REQ-SEC-040 | Certificate Validity Monitoring | The platform SHALL monitor TLS certificate expiry on all managed endpoints and SHALL alert the platform operations team and tenant admin (where applicable) at 30 days and 7 days before expiry; automated renewal (ACME/Let's Encrypt or customer-provided CA) SHALL be configured and tested in pre-production. | Security | Admin | Must | Expired certificates cause outages and alert security scanners; automation prevents human oversight failures |

### 3.2 Encryption at Rest

| ID | Title | SHALL Description | Category | Persona(s) | Priority | Rationale/Source |
|----|-------|-------------------|----------|------------|----------|-----------------|
| REQ-SEC-041 | Database Encryption at Rest | All relational databases (PostgreSQL, SQL Server, MySQL, Oracle) SHALL have transparent data encryption (TDE) or equivalent full-database encryption enabled; the encryption key SHALL be managed by the cloud KMS (for SaaS/VPC deployments) or an on-premises HSM/KMS (for on-prem); the database engine SHALL NOT store the DEK (data encryption key) without wrapping under the KMS. | Security | Admin | Must | GDPR Art. 32; HIPAA §164.312(a)(2)(iv); SOC 2 CC6.1; ISO 27001 A.10.1 |
| REQ-SEC-042 | Object Storage Encryption at Rest | All files stored in object storage (S3/Azure Blob/GCS/MinIO) SHALL be encrypted at rest using AES-256 (server-side encryption); encryption SHALL be enforced at the bucket/container policy level so that unencrypted PUTs are rejected; for BYOK customers, SSE-KMS with customer-managed keys SHALL be applied. | Security | Admin | Must | AES-256 is the industry standard for data at rest (NIST FIPS 197); SSE-KMS enables BYOK (V13) |
| REQ-SEC-043 | Field-Level Encryption for Sensitive Data | Designated sensitive fields (PII, API keys stored as tenant configuration, healthcare-identifiable data, legal-hold metadata, authentication secrets such as refresh tokens at rest) SHALL be encrypted at the application layer using AES-256-GCM with a per-tenant DEK, independent of the database-level TDE; this provides an additional encryption layer if the database is accessed via a compromised service account. | Security | Admin, Security-Admin | Must | Field-level encryption provides defense-in-depth beyond full-disk/TDE; enables per-tenant key rotation without re-encrypting the entire database |
| REQ-SEC-044 | Encryption Key Hierarchy | The platform SHALL implement a three-tier key hierarchy: (a) Root Key (KEK) — stored in KMS/HSM, never leaves the HSM boundary; (b) Tenant Master Key (TMK) — one per tenant, wrapped by the Root KEK, used to wrap DEKs; (c) Data Encryption Keys (DEKs) — one per data partition, wrapped by TMK, unwrapped on demand; key material SHALL never be stored in plaintext in any database or log. | Security | Admin | Must | NIST SP 800-57 key hierarchy; isolates impact of key compromise to a single tenant/partition |
| REQ-SEC-045 | BYOK — Customer-Managed Encryption Keys | The platform SHALL support Bring-Your-Own-Key (BYOK) where a tenant supplies a customer-managed key stored in their own KMS (AWS KMS CMK, Azure Key Vault, GCP Cloud KMS, on-prem PKCS#11 HSM); ESIP SHALL use the customer's KMS envelope-encrypt all tenant DEKs without ever taking custody of the customer's root key material; if the customer revokes their key, ESIP data SHALL become inaccessible within a configurable propagation window (target: ≤ 1 hour). | Security | Admin, Security-Admin | Must | BYOK is a procurement requirement for FSI, healthcare, and government; cross-ref V13 ONB-AK for the admin UI |
| REQ-SEC-046 | Encryption Key Rotation | The platform SHALL support periodic and on-demand key rotation at every tier of the key hierarchy; DEK rotation SHALL re-encrypt affected data partitions in the background without service interruption; the last rotation date, rotation period, and rotation status for each key SHALL be visible to Security Admins in the key management dashboard; rotation events SHALL be logged to the audit trail. | Security | Security-Admin | Must | Key rotation limits the blast radius of a compromised key; NIST SP 800-57 recommends ≤ 1-year rotation for DEKs |

### 3.3 Secrets Management

| ID | Title | SHALL Description | Category | Persona(s) | Priority | Rationale/Source |
|----|-------|-------------------|----------|------------|----------|-----------------|
| REQ-SEC-047 | Centralized Secrets Vault | All secrets (database passwords, AI provider API keys, SMTP credentials, object-storage access keys, signing keys, webhook secrets, connector OAuth tokens) SHALL be stored in a centralized secrets vault (HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, or a self-hosted equivalent for air-gapped deployments); the .NET API SHALL retrieve secrets dynamically at runtime via the vault API; secrets SHALL not be stored in environment variables, Kubernetes ConfigMaps, or application configuration files in plaintext. | Security | Admin | Must | Centralized vault is the industry baseline for secrets hygiene; NIST SP 800-53 SC-28; CIS Benchmark K8s 4.1.1 |
| REQ-SEC-048 | No Secrets in Source Code | No secret, credential, API key, certificate private key, or token SHALL be committed to the source code repository (any branch, any commit history); a secret-scanning tool (e.g., GitGuardian, TruffleHog, GitHub Advanced Security secret-scanning) SHALL run in the CI pipeline and SHALL block merges that introduce detected secrets; pre-commit hooks for secret detection SHALL be provided to all developers. | Security | Admin | Must | Source code repositories are frequently accessed by a large population; secrets in git are one of the most common breach vectors |
| REQ-SEC-049 | No Secrets in Container Images | Docker/OCI container images SHALL NOT embed secrets, API keys, or credentials; images SHALL be built with secrets passed via build secrets (BuildKit `--secret`) or retrieved at container startup from the vault; image scanning in CI SHALL verify absence of hard-coded secrets before publishing to the container registry. | Security | Admin | Must | Container image registries are often broadly accessible; embedded secrets survive image tagging and sharing |
| REQ-SEC-050 | Secret Rotation Without Service Restart | The secrets vault integration SHALL support dynamic secret rotation (database credentials via vault database secrets engine, or vault agent sidecar) such that secrets can be rotated without requiring a service restart or re-deployment; the .NET API SHALL refresh vault-sourced secrets at configurable intervals without dropping active connections. | Security | Admin | Must | Zero-downtime rotation is required for production systems; a rotation process that requires restart discourages frequent rotation |
| REQ-SEC-051 | Secret Access Audit Log | Every read and write to the secrets vault SHALL be logged with: requester identity (service account / user), secret path, operation (read/write/delete), timestamp, and outcome; the vault audit log SHALL be shipped to the SIEM (§8) and retained for ≥ 1 year; alerts SHALL be generated for anomalous secret access patterns (e.g., a service reading secrets outside its declared paths). | Security | Security-Admin | Must | NIST SP 800-53 AU-9; vault audit logs are a critical forensic artifact in the event of credential compromise |

## 4. SEC-UPL — Document Upload & File Security

> **Design principle (product owner's explicit ask):** Every file uploaded to ESIP — regardless of channel (Knowledge Hub connector, direct upload, whiteboard photo, import, mobile capture) — SHALL be scanned for malware and viruses by a pluggable, client-configurable scanning engine BEFORE the file is stored in the permanent storage backend or passed to any processing pipeline. Infected files SHALL never reach the application. CDR provides an optional additional hardening layer. The scanning architecture is an enterprise plugin point, not a fixed vendor choice.

### 4.1 Mandatory Pre-Storage Antivirus / Malware Scanning

| ID | Title | SHALL Description | Category | Persona(s) | Priority | Rationale/Source |
|----|-------|-------------------|----------|------------|----------|-----------------|
| REQ-SEC-053 | Mandatory AV Scan Before Storage | The platform SHALL antivirus/malware-scan EVERY uploaded file before writing it to any permanent storage location (object storage, database BLOB, local disk, network share); no file SHALL be accessible to end-users, AI pipelines, or downstream processing until its scan status is `CLEAN`; a file with `PENDING_SCAN` status SHALL be inaccessible and SHALL be treated as quarantined until the scan completes. | Security | All | Must | OWASP ASVS V12.2; file upload is one of the highest-risk surfaces in any enterprise SaaS; malware-infested documents can compromise connected systems and users |
| REQ-SEC-054 | Pluggable AV Engine Architecture | The AV/malware scanning subsystem SHALL implement a plugin/adapter architecture with the following first-class adapters: (a) **ClamAV** — open-source, self-hosted, suitable for on-prem/air-gapped deployments; (b) **ICAP protocol** — industry-standard content adaptation protocol enabling integration with ANY enterprise AV appliance (Symantec ProxySG, McAfee Web Gateway, Sophos, F-Secure, Check Point, Fortinet FortiGate, Cisco WSA, etc.); (c) **Microsoft Defender for Endpoint API** — cloud-based, suitable for Azure/Microsoft-aligned customers; (d) **Custom/BYO scanner** — a documented extension point accepting a scanner that implements the `IAntivirusScanner` interface; tenants configure their preferred adapter in the admin console; the platform SHALL ship with ClamAV as the default. | Security | Admin | Must | Enterprise customers have existing AV investments and compliance requirements mandating use of their approved scanner; ICAP is the RFC 3507 standard enabling interoperability with any compliant AV gateway |
| REQ-SEC-055 | ICAP Integration | The ICAP adapter SHALL support RFC 3507 ICAP 1.0; it SHALL be configurable with: ICAP server hostname/port, REQMOD vs. RESPMOD mode, service name, TLS (ICAPS), connection pooling parameters, and timeout; the adapter SHALL retry on transient ICAP server errors and SHALL fail-closed (reject the upload) on persistent ICAP unavailability unless the admin has explicitly configured fail-open mode (with mandatory alert). | Security | Admin | Must | RFC 3507; ICAP is the de-facto standard for enterprise AV proxy integration; fail-closed default is required for security posture |
| REQ-SEC-056 | Quarantine on Detection | When a scan detects malware, virus, ransomware, or a suspicious payload (any non-CLEAN result): (a) the file SHALL be moved to an isolated quarantine storage partition with no public/user read access, (b) the upload SHALL return an error to the user (non-disclosing: "The file was rejected by the security scanner — contact your admin"), (c) a high-priority security alert SHALL be generated to the tenant's Security Admin, (d) the event SHALL be written to the tamper-evident audit log (§8), (e) the quarantined file SHALL be retained for admin forensic review for a configurable period (default: 30 days) then securely deleted; the file SHALL NEVER reach object storage or any AI pipeline. | Security | Admin, Security-Admin | Must | Industry standard quarantine workflow; disclosure of malware type or signature to the end-user is a security risk (helps attacker evade); admin visibility is required for incident response |
| REQ-SEC-057 | Scan Status Surfaced to Users | The upload UI SHALL surface AV scan status to the user: files in `PENDING_SCAN` state SHALL show a "Scanning…" indicator; `CLEAN` files SHALL show a "Verified" badge; files that fail scan SHALL show a generic "Rejected by security policy" message; no scan verdict detail (malware name, signature, engine output) SHALL be shown to the end-user; admin-role users SHALL see full scan status including engine response in the Security Events panel. | Security | All | Must | Users need to know their upload completed or failed; security detail must be restricted to prevent evasion; cross-ref REQ-SEC-056 |
| REQ-SEC-058 | Asynchronous Scan with Held Access | Where AV engine processing time is non-trivial (large files, slow ICAP server), the scan SHALL be performed asynchronously; the file SHALL be held in a pre-storage quarantine area during scanning; the uploader SHALL receive a `202 Accepted` response with a job ID; when scanning completes, the upload SHALL either be committed to storage (CLEAN) or rejected (INFECTED/FAILED); the user SHALL receive a notification (in-app + optionally email) on scan completion; maximum scan wait time SHALL be configurable (default: 10 minutes; alert after threshold). | Security | All | Must | Large architecture documents (PDFs, Visio files, ZIP imports) may be tens of MB; synchronous scanning would time out HTTP connections |
| REQ-SEC-059 | Re-Scan on Engine Update | The platform SHALL support triggering a re-scan of previously stored files when the AV engine's signature database is updated to a materially newer version; re-scan SHALL be schedulable by the Security Admin and SHALL not disrupt user access to already-CLEAN files during re-scanning; any file that fails re-scan SHALL be automatically quarantined and its users notified. | Security | Security-Admin | Should | New malware signatures may detect threats missed by older engines; stored files are only as safe as the engine that scanned them |

### 4.2 Content Disarm & Reconstruction (CDR)

| ID | Title | SHALL Description | Category | Persona(s) | Priority | Rationale/Source |
|----|-------|-------------------|----------|------------|----------|-----------------|
| REQ-SEC-060 | Optional CDR per Tenant/File-Type | The platform SHALL support Content Disarm & Reconstruction (CDR) as an optional additional layer, configurable per tenant and per file type; CDR SHALL strip potentially malicious active content (macros, embedded scripts, hyperlinks to external domains, OLE objects) from document formats (DOCX, XLSX, PPTX, PDF) and reconstruct a clean version of the document preserving passive content (text, images, tables); CDR SHALL run after AV scan and before final storage commitment. | Security | Admin, Security-Admin | Should | CDR addresses zero-day threats not yet in AV signatures; particularly valuable for government and FSI customers with high document-borne threat environments; Votiro, OPSWAT, Glasswall are market examples |
| REQ-SEC-061 | CDR Engine Pluggability | The CDR subsystem SHALL implement the same plugin/adapter architecture as AV scanning (REQ-SEC-054), with adapters for: (a) a platform-provided open-source CDR library for basic macro/script stripping, (b) OPSWAT MetaDefender ICAP integration (enterprise CDR), (c) Glasswall Embedded Engine (SDK adapter), (d) custom CDR adapter via `IContentDisarmEngine` interface; tenants configure and disable CDR per file type in the admin console. | Security | Admin | Should | Avoid vendor lock-in; enterprise customers use different CDR vendors |
| REQ-SEC-062 | CDR Audit Trail | When CDR is applied, the platform SHALL record: original file hash (SHA-256), disarmed file hash, CDR engine used, content elements removed (type counts, not content), timestamp, and operator identity; this record SHALL be linked to the artifact version and exposed in the artifact's security metadata panel for Security Admins. | Security | Security-Admin | Should | CDR audit trail supports forensic analysis and compliance evidence |
| REQ-SEC-063 | CDR Failure Handling | If CDR processing fails (engine error, unsupported format, corrupt input), the platform SHALL treat the file as if CDR was not applied and SHALL flag it with a `CDR_FAILED` status visible to Security Admins; the admin SHALL be able to configure whether CDR failure blocks the upload (fail-closed) or allows it with a warning (fail-open with alert); default is fail-open with mandatory Security Admin alert when CDR is enabled. | Security | Admin | Should | CDR is an additional layer, not the primary control; fail-closed for CDR could block legitimate files if CDR engine has issues; admin choice is appropriate |

### 4.3 File-Type & Size Validation

| ID | Title | SHALL Description | Category | Persona(s) | Priority | Rationale/Source |
|----|-------|-------------------|----------|------------|----------|-----------------|
| REQ-SEC-064 | File-Type Allowlisting | The platform SHALL enforce a tenant-configurable allowlist of permitted file types per upload context (Knowledge Hub document upload, import file, whiteboard photo, CV attachment, template file); file type SHALL be validated by inspecting file magic bytes (signature), NOT by relying on the client-declared file extension or MIME type; uploads with file types not on the allowlist SHALL be rejected with an informative error before scanning. | Security | Admin | Must | OWASP ASVS V12.1; extension spoofing (e.g., `.jpg` containing a PE executable) is a fundamental upload attack; magic byte validation is reliable |

| REQ-SEC-066 | Archive Bomb Protection | Compressed archives accepted for bulk import (ZIP, TAR.GZ, 7Z) SHALL be validated for compressed-to-uncompressed expansion ratio; archives exceeding a configurable expansion ratio threshold (default: 100:1) or exceeding the uncompressed size limit SHALL be rejected; extraction SHALL be performed in a sandboxed, resource-limited environment; nested archive depth SHALL be limited (default: max 3 levels). | Security | Admin | Must | Zip bomb / archive bomb is a classic resource-exhaustion attack against document-processing systems |

## 5. SEC-STG — Configurable Storage Targets

> **Design principle (product owner's explicit ask):** The admin SHALL configure WHERE uploaded files, generated artifacts, deliverables, and Knowledge Hub content are stored. Storage is a pluggable port — cloud object storage, on-premises object store, local disk, or network share — configured per tenant, with encryption, retention, and access control requirements applied uniformly across all targets. No customer should be forced to store data in a cloud bucket they do not control.

### 5.1 Storage Target Configuration

| ID | Title | SHALL Description | Category | Persona(s) | Priority | Rationale/Source |
|----|-------|-------------------|----------|------------|----------|-----------------|
| REQ-SEC-068 | Storage Target Configuration by Admin | The platform SHALL allow the Tenant Admin (or Platform Admin for self-hosted) to configure the storage target for uploaded files and generated artifacts from the following options via the Admin > Storage Configuration panel: (a) **Cloud object storage — AWS S3**, (b) **Cloud object storage — Azure Blob Storage**, (c) **Cloud object storage — Google Cloud Storage**, (d) **S3-compatible on-premises — MinIO**, (e) **Local disk — platform-managed volume** (Kubernetes PersistentVolume or host path for single-node), (f) **Network share — SMB/CIFS mount**, (g) **Network share — NFS mount**, (h) **Customer-owned cloud bucket (BYO-Storage)** — the customer supplies their own S3/Blob/GCS bucket credentials and ESIP writes directly to it; the active storage target SHALL be set per-tenant and SHALL be changeable with a migration runbook that transfers existing files to the new target. | Security | Admin | Must | Explicit product owner requirement; enterprises have data residency, security classification, and cost requirements that dictate storage location; VPC-deployed and on-prem customers must not be required to use vendor-managed cloud storage |
| REQ-SEC-069 | Storage Abstraction Port | All application code SHALL write and read files through a storage abstraction port (`IFileStorage` interface in the .NET API); no application code SHALL directly reference an AWS SDK, Azure SDK, or local file-system path; storage adapters (S3Adapter, AzureBlobAdapter, GCSAdapter, MinIOAdapter, LocalDiskAdapter, SMBAdapter, NFSAdapter, BYOStorageAdapter) SHALL implement `IFileStorage` and be injected at runtime based on the tenant's configured storage target. | Security | Admin | Must | Ports-and-adapters principle (TECH-STACK.md); prevents vendor-specific code from proliferating in business logic |
| REQ-SEC-070 | Per-Tenant Storage Isolation | Files belonging to different tenants SHALL be stored in logically isolated containers: separate S3 buckets (or a single bucket with mandatory prefix+policy isolation), separate Azure Blob containers, separate MinIO buckets, or separate directory paths on shared storage; the `IFileStorage` layer SHALL enforce the tenant prefix on every read and write and SHALL reject requests that attempt to construct paths escaping the tenant's storage partition. | Security | Admin | Must | Multi-tenancy isolation at the storage layer (cross-ref V11 PLT-MT); a compromised application service account SHALL only access one tenant's files |
| REQ-SEC-071 | BYO-Storage (Customer-Owned Bucket) | When the tenant configures BYO-Storage (customer-owned S3/Blob/GCS bucket), ESIP SHALL: (a) accept bucket name, region, and access credentials (IAM role ARN for IRSA, SAS token, or access-key pair stored in vault — REQ-SEC-047); (b) validate read/write access at configuration time; (c) write all new uploads to the customer's bucket via the standard `IFileStorage` port; (d) never cache or duplicate customer data in ESIP-managed storage after BYO-Storage is active; (e) surface bucket validation status and last-successful-write timestamp in the admin console. | Security | Admin | Must | BYO-Storage is a procurement requirement for customers who must retain custody of all data in their own cloud accounts |
| REQ-SEC-072 | Storage Credential Rotation for BYO-Storage | BYO-Storage credentials stored in the vault SHALL be rotatable without service interruption; the admin SHALL be able to update credentials via the Admin > Storage Configuration panel; the platform SHALL validate new credentials before deactivating old ones; outdated credential events SHALL be logged. | Security | Admin | Must | Credential rotation for storage access is a periodic security maintenance requirement |

> **Design principle:** Every tenant's data is treated as if it belongs to a separate sovereign entity. Logical isolation is the baseline; physical isolation (dedicated database, dedicated storage) is an option for higher tiers. Data classification, DLP, and residency controls ensure that data handling matches the sensitivity of the content.

## 7. SEC-SDLC — Secure SDLC & Product Security

> **Design principle:** Security is engineered in from the start, not scanned for at the end. The ESIP CI/CD pipeline is a security gate, not just a build gate. Every commit, every dependency update, and every release is evaluated against a security checklist. The product itself is a threat model subject.

### 7.1 SAST, DAST & Secret Scanning

| ID | Title | SHALL Description | Category | Persona(s) | Priority | Rationale/Source |
|----|-------|-------------------|----------|------------|----------|-----------------|

## 9. SEC-AI — AI-Specific Security

> **Design principle:** The AI subsystem is both a capability and an attack surface. Prompt injection, model data exfiltration, and output exploitation are real threats that require first-class controls — not post-hoc patches. The "no training on customer content" guarantee is an irrevocable product commitment enforced architecturally, not by policy alone.

### 9.1 Prompt Injection & Jailbreak Defense

| ID | Title | SHALL Description | Category | Persona(s) | Priority | Rationale/Source |
|----|-------|-------------------|----------|------------|----------|-----------------|
| REQ-SEC-124 | Prompt Injection Defense | The platform SHALL implement defenses against prompt injection attacks (both direct injection via user-supplied content in prompts, and indirect injection via malicious content embedded in ingested documents that is then included in RAG context): (a) system prompt separation — user-supplied content SHALL be inserted in a clearly delimited user-message boundary, never injected into the system prompt; (b) structured prompt construction — prompts SHALL be built via parameterized templates (V06, PLT-PRM), not string concatenation of user input; (c) input sanitization — user content that is included in prompts SHALL be stripped of known injection patterns (`\n\nHuman:`, `<|im_end|>`, `IGNORE ALL PREVIOUS`, etc.) before prompt construction. | Security | All | Must | OWASP LLM Top 10 2025 LLM01 (Prompt Injection); prompt injection is the most prevalent AI application attack |
| REQ-SEC-125 | Indirect Prompt Injection via RAG Defense | When Knowledge Hub documents are retrieved as RAG context and included in AI prompts, the platform SHALL treat retrieved document content as UNTRUSTED input; document content SHALL be wrapped in explicit role delimiters (e.g., `<retrieved_document>` tags) that the system prompt instructs the model to treat as external data, not instructions; documents known to contain injection attempts (detected by pattern scan or AV flag) SHALL be excluded from RAG context automatically. | Security | All | Must | OWASP LLM Top 10 LLM01; indirect injection via RAG is a documented attack where a malicious document in the knowledge base hijacks the AI response |
| REQ-SEC-126 | Jailbreak Detection & Logging | The platform SHALL maintain a jailbreak detection layer that identifies common jailbreak patterns in user prompts (roleplaying as unguarded models, direct instruction override attempts, DAN-style prompts, encoded instruction bypass) and SHALL: (a) block the request, (b) return a safe response indicating the action is not supported, (c) log the attempt with full prompt content (truncated for size) to the security audit log, (d) generate a security alert if the same user account has ≥ 3 jailbreak attempts within 24 hours. | Security | All | Must | OWASP LLM Top 10 LLM01; repeated jailbreak attempts may indicate targeted attack; logging enables forensics |
| REQ-SEC-127 | Prompt/Response Content Filtering | The platform SHALL apply configurable content filters on AI model input and output: (a) input: block prompts requesting generation of malicious code, PII exfiltration, or content violating the platform's use policy; (b) output: filter model responses for accidental PII disclosure, sensitive data that was not in the user's context, harmful content; filters SHALL be configurable per tenant and per AI task type; guardrail configuration SHALL be version-controlled and audited (cross-ref V06 §11). | Security | Admin | Must | OWASP LLM Top 10 LLM02 (Insecure Output Handling); AI content filtering is a layer between the model and the user |

## Appendix B — Catalog-Wide Rulings Applied

Per `00-MASTER-INDEX.md` §6:

1. **Priority ≠ Phase.** `Must` means "required in the product." Build sequence is governed by `BUILD-PLAN-MVP-AND-PHASING.md`. Server-side enforcement (SEC-SSE) and upload AV scanning (SEC-UPL) are high-priority early items given that the current Firebase direct-call pattern is a security concern. This volume is a **Phase 2–3** volume (backend .NET API is a prerequisite for most controls).
2. **No training on customer data.** REQ-SEC-130 implements and enforces the master-index ruling for the AI layer; this is the architectural enforcement mechanism, not merely a policy statement.
3. **Air-gapped mode.** AV scanning in air-gapped mode SHALL use ClamAV (REQ-SEC-054 adapter (a)) or a customer's on-prem ICAP server (adapter (b)); cloud-based AV APIs (e.g., Windows Defender cloud) are excluded from air-gapped deployments; local storage targets (REQ-SEC-077) replace cloud object storage.
4. **Provider names are illustrative.** All named AV vendors (ClamAV, Defender, OPSWAT, Glasswall), SIEM platforms (Splunk, Sentinel, Chronicle), and vault products (HashiCorp, AWS Secrets Manager) are illustrative of the adapter interface, not exclusive choices.
