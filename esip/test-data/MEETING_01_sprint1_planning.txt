MEI LIN [00:23]:
We looked at this. Two options. Option A: manual estimate — the technician sets an
estimated completion time when they start the job. Dispatchers see it. It's subjective.
Option B: we compute average job duration by job type from historical data, subtract
elapsed time. More objective but ignores job-specific complexity.

RAVI SHARMA [00:25]:
Option B is better for the automated pre-emption decision because it doesn't rely on
technician input. Technicians rushing through jobs to avoid pre-emption would be a bad incentive.

DEV KAPOOR [00:26]:
Agreed. Let's go Option B: computed remaining_time_estimate = avg_duration_for_job_type - elapsed_time_since_start.
I'll add this to the WorkOrderService. We need a job_type_durations reference table.
That's a new table — I'll add it to the schema delta. Should take about three days.

PRIYA NAIR [00:27]:

[ITEM: ETA cache design]
DEV KAPOOR [00:31]:
Next: the ETA cache design. My proposal from the chat: 90-second TTL for Normal and High SLA,
20-second TTL for Critical SLA. Cache populated by a background service that calls Google Maps
every 90 seconds for all active technicians. Synchronous auto-assign endpoint reads from cache.
Cache miss → Haversine fallback, async refresh queued.

RAVI SHARMA [00:33]:
One concern: what if the cache service crashes? The auto-assign endpoint falls back to Haversine
permanently until the cache recovers. Haversine accuracy is ±25% on congested urban routes.
We should have a health check on the cache service that the auto-assign endpoint can use to
decide whether to return a stale ETA or flag it as estimated.

DEV KAPOOR [00:35]:
Fair. We add a field to the auto-assign response: etaSource: "google_maps_cached" | "haversine_fallback" | "google_maps_live".
The Dashboard can show a small indicator when the ETA is an estimate.

PRIYA NAIR [00:36]:
I like that. It's honest to the dispatcher about data quality. I'll add etaSource to the
API spec and the Dashboard UI design.
