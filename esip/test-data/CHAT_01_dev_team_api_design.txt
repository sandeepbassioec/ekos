Dev Kapoor [09:20] First one: the PRD says location pings go every 30 seconds when a job is
"In Progress or Travelling". But those are two different job statuses. Travelling is when the
tech is en-route to the job, In Progress is when they're on-site. The ping frequency probably
should be different — every 30s while Travelling makes sense (moving), but every 30s while
stationary on-site is wasteful and will drain battery faster.

My suggestion: 30s while Travelling, 5-minute interval while In Progress (on-site).
This also reduces location pings by ~65% for on-site time.

client-side logic change beyond "respect the interval the server returns".

Dev Kapoor [09:42] 👍 updating spec. Second question — bigger one.

The auto-assign endpoint: POST /api/v2/fieldops/dispatch/auto-assign — the PRD says it's
synchronous with a 5-second timeout. But consider this scenario: 200 concurrent dispatch
requests arrive simultaneously (big storm event, lots of jobs created at once). Each one
needs to call Google Maps for ETA computation. Google Maps Routes API is external. If Google
has a 1-second response time under load, 200 concurrent → 200 parallel Google Maps calls.
We'll hit our rate limit immediately.

I think we need to rethink this. Options:
A) Async dispatch: POST returns a jobDispatchId immediately, client polls GET /dispatch/{id}/status
B) Synchronous but with in-memory ETA cache (TTL 90s) so we don't always hit Google Maps
C) Synchronous but use Haversine for the sync response and update with real ETA async

─────────────────────────────────────────────────────────────────
Ravi Sharma [09:55] Option B is my preference. We already have a location cache for
technician positions (we update it every 30s from pings). We can pre-compute ETAs for all
active jobs every 90s as a background task and cache the results. The sync endpoint just
reads from cache. Cache miss → Haversine fallback, async update queued.

─────────────────────────────────────────────────────────────────
Mei Lin [09:57] Option B works but we need to be careful about cache staleness. If a tech
just diverted around traffic and their ETA jumped from 12min to 35min, the cached value
could be stale for up to 90s. For SLA-critical assignments that 90s window matters.

─────────────────────────────────────────────────────────────────
Dev Kapoor [10:02] Good point. Compromise: cache TTL 90s for Normal/High SLA jobs, 20s
TTL for Critical SLA jobs. Critical jobs always trigger a fresh Google Maps call if cache
is stale. Thoughts?
