## 🔌 2. The Generic Update Mechanism for Any Artifact Type

Hamare platform mein har artifact type ke liye **"Update Triggers"** define hote hain, jo external systems ya internal graph events se aate hain.

| Artifact Type | Update Trigger Sources | Automatic Action |
|---------------|------------------------|------------------|
| **Functional Requirement** | - Jira/Azure DevOps story changes<br>- Git commit message mentioning requirement ID<br>- User feedback widget me related pain point<br>- AI parses customer email and links to requirement | Requirement node updates its "Last Verified" timestamp, status; AI re-evaluates scope completeness. |
| **Non-Functional Requirement** | - Performance test results (from CI)<br>- Monitoring alerts (Prometheus/Datadog connector)<br>- Cloud cost changes (FinOps connector) | NFR node updates its "Compliance Status" and if violation, triggers Risk creation. |
| **Business Process (BPMN)** | - Process mining tools (Celonis connector)<br>- Actual user clickstream data (Analytics connector)<br>- Support ticket patterns | BPMN widget highlights steps that are causing bottlenecks or are rarely used. AI suggests process redesign. |
| **Risk / Assumption** | - New CVE database entry (Security connector)<br>- Dependency health checks (Snyk/OWASP)<br>- AI horizon scanner detects trend shift | Risk node re-evaluates probability/impact; if assumption invalidated, linked decisions flagged. |

## 🧠 Core Strategy: Peer-to-Peer (WebRTC) + Self-Hosted Signaling

### Technology Base
- **WebRTC**: Browser aur native apps mein built-in real-time communication. Direct peer-to-peer audio/video/data channels, encrypted end-to-end (DTLS-SRTP). No central server for media.
- **Signaling Server**: Sirf connection establish karne ke liye chahiye (offer/answer SDP, ICE candidates exchange). Ye ek chhoti si WebSocket/HTTP service hai, jiska data volume negligible hai. Ham ek reference signaling server denge (open-source, Docker image). Consumer ise apne VPC, on-prem, ya air-gapped network mein host kar sakta hai.
- **STUN/TURN Servers**: For NAT traversal, basic STUN servers free/public use kar sakte hain (Google STUN). Agar enterprise firewall ke peeche ho, to consumer apna TURN server bhi host kar sakta hai (jaise coturn). Ye bhi self-hosted ho sakta hai, aur media relay cost consumer ki infrastructure pe aayegi.

### How It Works in EKOS / EKR Viewer
1. **Session Initiation**: EKOS widget ya EKR Viewer mein “Ask Live” button dabaya. Viewer ek session request create karta hai (graph node `LiveSessionRequest`). Is request mein `session_topic` (which widget, artifact ID), `proposed_participants`, `signaling_server_url` (jo consumer ne configure kiya) hota hai.
2. **Signaling**: Platform ka lightweight signaling service (jo consumer ke apne server par hai) participants ko notify karta hai, aur WebRTC connection establish karwata hai. Agar user offline hai, to push notification (via platform connector) bhej sakte hain, lekin signaling data sirf usi self-hosted server se hoga.
3. **Media Direct**: Ek baar connection ban gaya, saara audio/video/data (cursor sync, drawing, etc.) direct participants ke beech encrypted flow hoga. Hamari taraf se koi media packet touch nahi hoga.
4. **Session Recording**: Agar recording chahiye, to woh kisi ek participant ka client locally record karega (encrypted) aur session end hone par us file ko apne EKOS graph mein `SessionRecording` node ke roop mein attach kar dega (ya phir EKR bundle mein daal dega). Recording storage bhi consumer ki taraf.
5. **EKR Viewer Integration**: Viewer ke andar WebRTC stack pre-bundled hoga. Signaling server URL ek configurable setting hogi (enterprise admin set karega). Free users ke liye, ham ek public STUN server ka default de denge aur optional lightweight signaling bhi, lekin media still P2P. Bandwidth aur CPU/GPU encoding viewer ke local machine par lagega.

### Infrastructure Responsibility Split
| Component | Provided by Platform | Provided by Consumer |
|-----------|----------------------|----------------------|
| WebRTC client libraries (inside EKOS/Viewer) | ✅ Built-in | ❌ |
| Signaling server (lightweight) | ✅ Reference implementation (open-source) | Consumer hosts on own infrastructure |
| STUN server | ✅ Public ones (google, etc.) for ease | Consumer can host own TURN if needed |
| TURN server (media relay) | ❌ (optional, rare) | Consumer hosts if symmetric NAT |
| Media processing/streaming | ❌ | Direct P2P, consumer devices |
| Session recording storage | ❌ | Consumer local/own cloud |
| Session metadata (graph node) | ✅ Platform graph | ❌ |

Is model mein hamara marginal cost sirf signaling server ki light traffic hai, jo ek chhota sa Docker container hai. Agar consumer fully air-gapped hai, to signaling server bhi unke andar, hamara koi server touch hi nahi hoga.

## 🔐 1. Core Principle: Zero Credential Storage, Maximum Controlled Access

Hamara platform **kabhi bhi raw credentials (username/password) store nahi karega**. Iske bajay, hum industry-standard delegation aur tokenization use karenge:

- **OAuth2 / OIDC:** Agar document kisi modern identity provider (Azure AD, Okta, Google Workspace) ke peeche hai, toh EKOS ko sirf delegated access token milega, jo limited scope aur expiry ke saath hoga.
- **API Keys / Service Accounts:** For programmatic access, customer apne system mein ek dedicated service account banayega, jiska key EKOS ke secret vault mein encrypted store hoga (customer-managed KMS se unlock). Key rotation automated hogi.
- **Kerberos / SPNEGO:** Legacy Windows environments ke liye customer ke side par ek connector agent hoga jo Kerberos ticket handling karega.
- **Client Certificates:** Mutual TLS authentication ke liye certificate-based auth. Certificate customer ka apna PKI issue karega.

**Kabhi bhi raw password EKOS mein nahi aayega.**

## 🧱 2. Three-Layer Access Architecture

Har external secure resource ke liye teen access layers hain, depending on where resource hai aur use case:

### Layer 1: Self-Hosted Connector Agent (Firewall ke Andar)
Ye sabse powerful aur secure option hai. Customer apne internal network (on-prem ya private cloud) mein ek lightweight **EKOS Connector Agent** install karega (Docker container ya Windows service). Ye agent:

- Customer ke internal resources (file shares, SharePoint on-prem, internal wikis, databases) se directly baat karega.
- Saara data extraction, indexing, aur transformation yahin local machine par hoga; sirf structured metadata aur (optionally) sanitized content EKOS cloud/platform ko bhejega.
- Firewall rules: Agent sirf outbound HTTPS karega (port 443), koi inbound port nahi. So existing security posture kharab nahi hoga.
- Agent ko jo permissions milegi, woh customer ke existing IAM (Active Directory, LDAP) ke according hongi.
- Yeh agent EKOS platform se sirf commands lega ("fetch this document list, get updates for this requirement") aur results dega. Media files (images, videos) bhi agent ke through stream ho sakti hain, bina direct external access ke.

### Layer 2: Platform Vault & Just-in-Time Fetch
Jab kisi external resource ko EKOS widget mein reference karna hai, platform uske URL aur access method ko store karega, but not credentials. Jab viewer/platform ko actual content fetch karna ho, wo do tariko se kar sakta hai:

- **Server-Side Fetch (Platform Connector):** Agar resource publicly accessible nahi hai but platform ke paas authorized token (stored in vault) hai, toh EKOS backend woh token use karega, resource fetch karega, process karega, aur viewer ko result dega. Token vault hardware security module (HSM) ya cloud KMS se secured rahega.
- **Client-Side Fetch (Viewer with user's own session):** Agar resource user ke personal credentials se accessible hai (jaise Confluence page jisko sirf woh dekh sakta hai), toh EKOS Viewer user ke existing browser/SSO session ka fayda uthayega. Viewer ek sandboxed iframe ya native webview open karega jisme user pehle se authenticated hai. Phir wahan se content extract karega local processing ke liye. Isme koi additional credential sharing nahi.

### Layer 3: Offline Bundle with Embedded Content (Pre-Fetched)
EKR bundle banate waqt, creator decide karega ki external references ko bundle mein embed karna hai ya nahi.

- Agar "Embed" option choose karega, toh platform (ya on-prem agent) uss waqt resource ko fetch karega (using allowed access), usko encrypt karega, aur bundle mein include karega. Viewer offline bhi bina kisi auth ke dekh sakega.
- Agar resource fetch nahi ho paya (no access), toh bundle create karte waqt warning aayegi, aur creator ke paas teen choices hongi:
  1. Skip (reference broken rahega).
  2. Embed a placeholder (jaise summary text, metadata).
  3. Use AI to generate a surrogate summary from the context around the reference (using previously cached data).

## 🔐 1. Core Principle: Zero Credential Storage, Maximum Controlled Access

## 🧱 2. Three-Layer Access Architecture

### Layer 1: Self-Hosted Connector Agent (Firewall ke Andar)

Isme koi additional credential sharing nahi.

## 🧠 Core Philosophy: EKOS as a Reactive Knowledge Graph

Har baat, har action — chahe kisi ne comment likha, kisi ne review sign kiya, ya kisi ne bundle khola — woh ek **immutable event** ban jaati hai. Ye events graph mein store hote hain, aur ek rules engine unhe sunta hai. Rules engine decide karta hai ki ab kya karna hai: kisi ko notify karo, ek webhook fire karo, ya internal workflow trigger karo.

Yeh koi alag module nahi, balki ontology ka hissa hoga: `Event` node type. Har event ka source, timestamp, aur payload hoga. Ye events streamable hain via WebSockets aur Webhooks.

## ⚡ 1. Event-Driven Engine (EDE) — Design

### Event Types (Core Ontology)
Har user action ke liye predefined events, par custom events bhi users bana sakte hain:

| Event Type | Triggered When | Example Payload |
|------------|----------------|-----------------|
| `artifact.created` | Koi naya requirement/story/decision bana | `{artifact_id, type, creator}` |
| `artifact.updated` | Property ya link change hui | `{artifact_id, changed_fields}` |
| `artifact.reviewed` | Kisi ne review sign kiya (like digital signature) | `{artifact_id, reviewer, verdict}` |
| `artifact.commented` | Comment thread start hui | `{artifact_id, comment_id, author}` |
| `bundle.opened` | EKR Viewer mein bundle khola | `{bundle_id, viewer_id, device_info}` |
| `bundle.consumed` | Self-destruct bundle destroy hua | `{bundle_id, viewer_id, timestamp}` |
| `session.started` | Live collaboration session shuru | `{session_id, participants}` |
| `clarification.resolved` | Doubt resolved hua | `{request_id, resolver}` |
| `policy.violated` | Governance policy breach hui | `{policy_id, violating_node_id}` |

### Internal Workflow Engine (Built-in)
- **Rules Config:** Admin ek low-code rule builder se define kare: `WHEN event = 'artifact.reviewed' AND verdict = 'rejected' THEN assign to original creator with priority high`.
- **Workflow Steps:** Sequence, parallel, approval, delays. Sab kuch graph nodes ke roop mein (BPMN-lite ontology se already hai).
- **Webhook Dispatcher:** Har rule ek webhook fire kar sakta hai — kisi bhi external system ko POST bhejega with structured JSON (CloudEvents format). Isse Jenkins, ServiceNow, Slack, ya custom tool integrate ho jaate hain.

### Event Bus Architecture
- EKOS ke backend mein Apache Kafka (ya lighter Redis Streams for on-prem) hoga. Har event ek topic par publish hoga.
- Connector Agent (firewall ke andar) bhi events ko securely consume kar sakta hai.
- EKR Viewer offline ho, toh events local queue mein store hote hain, online aate hi sync ho jaate hain.

## 🔐 2. Authorization Strategy — OAuth2 Authorization Code Flow with PKCE

Hamara design **hardcoded username/password** ko hamesha avoid karega, lekin agar customer extreme legacy systems ke liye force karein, to encrypted vaulting ka option denge (with strong audit trail). Primary mechanism OAuth2 / OIDC hoga.

### Flow for EKR Viewer:
1. **Viewer Registration:** EKR Viewer ek OAuth2 client ki tarah register hoga with the target system (Jira, GitLab, Azure DevOps, custom). It gets a `client_id`.
2. **User Initiation:** Jab user preview maange, Viewer ek secure system browser ya embedded WebView (with sandboxed context) open karega. Ye browser target system ke `/authorize` endpoint par redirect karega with `response_type=code`, `code_challenge` (PKCE), aur `redirect_uri` (a custom scheme ya localhost loopback).
3. **User Consent:** User apne existing credentials se login karega (agar pehle se logged in hai, to consent screen bhi skip ho sakti hai). Target system permission maangega.
4. **Token Exchange:** Authorization code milne par Viewer usi loopback/redirect se code grab karega aur token endpoint se `access_token` aur optional `refresh_token` le lega (PKCE ke saath). Yeh exchange backend channel (Viewer से directly token endpoint तक) hoga, bina kisi intermediary ke.
5. **Secure Storage:** Access token ko Viewer ke local secure storage (OS Keychain/Keystore) mein save karega, expiry tak.
6. **API Calls:** Ab Viewer linked resource ke REST API ko access token ke saath call karega, data fetch karega, aur preview render karega.
7. **Token Refresh:** Agar refresh token hai, to automatically renew karega.

### Offline Handling:
- Agar Viewer pehle se online tha aur token refresh cycle chal rahi hai, to preview ke liye latest data cached hoga.
- Agar puri tarah offline hai, to embedded bundle mein pre-fetched data dikhega.

### Alternative: Client Certificate / Mutual TLS
Government aur high-security environments ke liye, OAuth2 ki jagah client certificate-based mutual TLS authentication use kar sakte hain. Viewer apne certificate (issued by org PKI) ke saath target system se direct connect karega.

2. **Daily Use:** Ab jab tu EKOS Studio mein kisi Requirement ke linked Jira Story ka preview karega, EKOS automatically tere vault se valid token fetch karega, Jira API call karega, aur data dikha dega. Agar token expire ho gaya, EKOS apne refresh token se naya token le lega — sab kuch background mein.
3. **EKR Viewer:** Jab tu apne laptop pe EKR Viewer kholta hai aur apne EKOS account se sign-in karta hai (online mode), Viewer tere vault se tokens ko securely sync kar leta hai (encrypted local storage). Phir tu offline bhi linked resources ke pre-fetched previews dekh sakta hai. Agar online hai aur preview fresh karna hai, Viewer directly token use karega (client-side API call) — bina kisi extra login ke.
4. **Multiple Devices:** Tera vault cloud-synced rahega (end-to-end encrypted with teri master key). Toh tu apne phone ke EKR Viewer mein bhi same seamless experience payega.

### Security Design:
- **Zero-Knowledge Vault:** EKOS backend kabhi bhi tera raw token decrypt nahi kar sakta unless tu usko explicit permission de (for server-side previews). Default mein, encryption key teri client-side derived hoti hai (your password + hardware-bound key). So server can only store encrypted blobs; client decrypts them when needed.
- **Fine-Grained Access:** Tu decide kar sakta hai ki kaunse apps ko kaunse tokens available hain. EKOS Studio ke "Jira Widget" ko sirf Jira token milega, Git token nahi.
- **Token Expiry & Rotation:** Refresh tokens automatically manage hote hain. Agar kisi system ka token revoke ho gaya, EKOS tujhe notify karega.
- **Audit:** Har token usage log hoga — kaunsi API call kab, kahan se, kyun.

## 🔍 2. Detection Mechanism — Automatic & Manual

### Automatic Detection (for Supported OS)
- EKR Viewer/Studio system-level events ka use karega:
  - **Windows:** `SetWindowDisplayAffinity` (WDA_EXCLUDEFROMCAPTURE) ya Desktop Duplication API se screen capture detection. Aur naye Windows 11 mein `ScreenCaptureSession` APIs.
  - **macOS:** `CGWindowListCreate` se window sharing check, ya `NSApplication` shared `isScreenRecording` property (with permission).
  - **Mobile (iOS/Android):** `UIScreen.isCaptured` ya `MediaProjection` indicators.
- Jaise hi OS signal aata hai ki screen capture active hai, EKR turant "Presentation Mode" activate kar dega (with a subtle toast notification).

### Manual Toggle (Override)
- User ek button press kar sakta hai "Enable Presentation Mode" – chahe screen share ho ya nahi (jaise projector pe dikhana ho).
- Yeh manual toggle administrative control hai, aur logs record karenge.

### Intelligent Heuristic
- Agar OS signal unavailable ho (e.g., browser-based EKOS Studio), to EKR aise heuristic use karega: sudden window obscuration, fullscreen mode, ya browser `getDisplayMedia()` API call monitoring. Ye optional hoga, with user consent.

## 🔓 4. Controlled Reveal — "Just This Once" Unmask

Tu ne sahi socha: "agar dikhana hi hai to activate kyun karega?" Lekin real-life mein zaroorat padti hai. Tab presenter ek **granular "Reveal Pass"** use karega.

### Reveal Pass Workflow
1. Presenter jab kisi masked element pe click karega (ya right-click), ek option aayega: **"Temporarily Reveal"**.
2. Presenter reason select karega (dropdown: "Legal review", "Client demo", etc.) aur duration set karega (e.g., 60 seconds).
3. EKR ek one-time **Reveal Token** generate karega (cryptographically signed, with expiry). Ye token sirf us specific node/widget ke liye valid hoga.

5. Poora action **immutable audit log** mein recorded hoga: "User X revealed artifact Y for Z seconds, reason: ..."

- **Approval Gate:** Agar environment ultra-sensitive hai, to reveal ke liye ek second person ki approval bhi maangi ja sakti hai (like a check from compliance officer). Ye workflow governance engine handle karega.

## 🦀 1. Rust-Based EKR Viewer: The Vision

Agar Rust use karein, to EKR Viewer ek single, highly optimized, memory-safe codebase se sab platforms (Windows, macOS, iOS, Android) ke liye compilable hoga. Core logic — encryption, graph processing, event handling, network stack — sab Rust mein likha ja sakta hai. Performance native ke barabar, binary size controlled, aur reverse-engineering mushkil (Rust binaries are hard to reverse).

Lekin widgets aur custom widget framework ke liye humein UI rendering ki zaroorat hai. Rust ka native UI ecosystem abhi mature nahi hai. Isliye do approach hain:

### Option A: Rust Core + WebView Shell (Hybrid)
- **Core (Rust):** All heavy lifting — cryptographic operations, secure storage, ABAC engine, event bus, connector logic, WebRTC management.
- **UI (WebView):** Wahi React widget code jo EKR Studio mein hai, use karo. Rust app ek WebView host karega (like Tauri, but for mobile also). Custom widgets jo React mein likhe gaye hain, woh bhi chalenge.
- **Communication:** Rust ↔ JavaScript bridge (JSON or custom protocol) se data exchange. Performance-critical rendering (like packet animation) WebGL/Canvas se hogi, jo WebView ke andar smoothly run kare.

### Option B: Pure Rust Native UI (No WebView)
- **UI Framework:** Use something like `egui`, `iced`, or `druid` for Rust native rendering.
- **Widget System:** Tu ko completely new widget SDK design karna padega in Rust. Custom widgets bhi Rust mein likhne honge, ya fir ek scripting language (Lua, Python) embed karni hogi.
- **Trade-off:** Existing React widgets reuse nahi ho sakte. Community ka adoption slow hoga kyunki zyada developers Rust nahi jaante. Time-to-market bahut high.

## ⚖️ 2. Detailed Comparison: Capacitor/Electron vs Rust Hybrid (WebView) vs Pure Rust

| Criteria | Capacitor/Electron (Current Recommendation) | Rust Core + WebView (Tauri-like) | Pure Rust Native UI |
|----------|----------------------------------------------|----------------------------------|----------------------|

4. **No repeated login prompts** — the token is silently refreshed if expired, using the stored refresh token.

**System and Method for Self‑Destructing, Hardware‑Bound Digital Knowledge Bundles with Copy Protection**

### Field of the Invention

### Background
Traditional digital documents (e.g., PDF) can be copied, shared, and viewed infinitely. DRM solutions rely on online license servers, which fail in air‑gapped environments. ### Summary
The invention provides a method for creating a self‑destructing knowledge bundle. A creator encrypts the content with a symmetric key and wraps this key using the recipient’s device‑specific hardware public key (e.g., TPM, Secure Enclave). Upon first open, the viewer attests the device, exchanges the nonce for a signed token from an activation server (or uses pre‑provisioned whitelist), and unwraps the content key. The viewer stores the key in volatile memory only, and after a predetermined time or view count, it cryptographically wipes the key and overwrites the file. ### Detailed Description
The system comprises a creation module and a viewer module. The viewer module, upon launch, verifies the device identity using hardware attestation, contacts an activation server (which may be local in air‑gapped mode) to obtain a time‑limited activation token, decrypts the DEK, and renders the content. A secure timer and view counter trigger the destruction routine: the DEK is zeroed, the file is overwritten with random data, and a destruction attestation is optionally sent.

### Claims
1. A method for secure distribution of digital content, comprising:
   - encrypting the content with a symmetric key;
   - encrypting said symmetric key with a public key bound to a hardware root of trust of a recipient device;
   - transmitting a bundle containing the encrypted content and encrypted key to the recipient device;
   - at the recipient device, decrypting the symmetric key only after successful attestation of the hardware root of trust;
   - rendering the content using the decrypted symmetric key stored exclusively in volatile memory;
   - and automatically destroying the symmetric key and overwriting the bundle after a predetermined condition is met, rendering any copies of the bundle inoperable.

2. The method of claim 1, wherein the predetermined condition is a time limit, a view count, or a combination thereof.

3. The method of claim 1, further comprising requiring a one‑time activation nonce that is verified by an activation server before decryption is allowed.

4. The method of claim 3, wherein the activation server is operable offline via a pre‑provisioned whitelist of device public keys.

5. A system comprising a processor and memory configured to perform the method of claim 1.

6. A non‑transitory computer‑readable medium storing the bundle, wherein the bundle is structured to be processed by the method of claim 1.

## 🛠️ The Bulletproof Upgrades: Deep-Dive Architectural Fixes

### 1. Rearchitecting the Multi-User Collaboration Layer (Fixing the WebRTC Mesh Bottleneck)

* **The Problem:** The suggested strategy relies on pure Peer-to-Peer (Mesh) WebRTC for live collaborative diagramming and video sessions to save on hosting costs. While this works beautifully for a 1-on-1 discussion, it degrades exponentially as more users join. In a mesh network, every participant must encode and upload their video, audio, and cursor stream to *every other participant* individually. If 8 architects join a Change Control Board meeting, each user's device must maintain 7 simultaneous upload streams. Low-powered laptops and mobile devices will drop frames, overheat, and cause lagging cursor synchronization, ruining the collaborative experience.
* **The Solution: The Self-Hosted Selective Forwarding Unit (SFU) Sidecar**
To preserve your brilliant **Bring Your Own Infrastructure (BYOI)** cost model while ensuring elite scalability, the platform must support a split-topology media architecture:
* **Standard Mode (Default):** For 2 to 4 participants, the system utilizes direct peer-to-peer WebRTC mesh routing.
* **Enterprise Scale Mode:** For larger review sessions, instead of relying on a costly central cloud media server, the enterprise admin deploys a lightweight, open-source **SFU container** (such as MediaSoup or Janus) directly inside their own secure perimeter (on-prem or private cloud).
* Each user uploads their data stream exactly *once* to this local container, which then efficiently forwards the data packets to the other participants. Because the infrastructure runs completely within the client's network boundary, your system data costs remain at zero, corporate data never leaves their firewall, and the visual workspace remains incredibly responsive at 60fps for dozens of simultaneous users.

### 2. The Hybrid Visual Runtime Architecture (Fixing the WebView Shell Lag)

### 3. Preventing the Sandbox Vault Context-Leak Vector

* **The Problem:** The "Sandbox Vault" is an excellent approach to privacy-preserving local AI analysis. However, it introduces a subtle but severe security vulnerability. If an engineer drops confidential system log files or internal trade-secret specifications into their local sandbox vault, and then asks the local AI to weave that context into an informational story or use-case description embedded within a `.ekr` bundle, the local AI will happily generate text that extracts and surfaces details from those protected files. * **The Solution: Semantic Exfiltration Filter & Local Leak Prevention (LLP)**
We must establish a strict boundary between the local sandbox vault and the exportable bundle generation engine:
* **The Sandbox Isolation Constraint:** The EKR Viewer engine must treat the local Sandbox Vault as a **Strict Read-Only Sink** for prompt expansion. You have executable widgets, AI, events, approvals, collaboration, and security. These all need a common execution model.

* Widget lifecycle
* Event dispatch
* Policy enforcement
* AI orchestration
* Collaboration sessions
* Transactions
* Offline synchronization

Without a runtime, features remain isolated.

This is the idea I keep coming back to because I think it's fundamental.

Instead of saying "EKOS imports Word, PDF, SAP, Jira, videos, emails..."

Think of EKOS as compiling heterogeneous sources into a canonical semantic representation.

Just as a programming language compiler translates many source constructs into an executable representation, the Knowledge Compiler translates enterprise artifacts into a living knowledge graph.

That shifts the conversation from "document management" to "knowledge computation."
