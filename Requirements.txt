# **VectorVolt Master Technical Scope & Architecture Blueprint**

## **1. Core Architectural Mandates & Non-Negotiables**
This engine operates on strict, unbreakable principles. Any compromise here destroys the latency budget.
* **Memory-First & Log-First Durability:** Business logic executes entirely in-memory. Every command is appended to a durable Write-Ahead Log (WAL) before in-memory state mutation and acknowledgment.
* **Zero-GC & Allocation Discipline:** The "Hot Path" is strictly allocation-free. We mandate `Span<T>`, `Memory<T>`, `ref struct`, and Object Pools. `new` is forbidden during execution.
* **Deterministic Processing:** Single-writer thread per shard. No internal locks (`Monitor`, `Mutex`).
* **Hardware Sympathy:** Thread-per-core pinning (isolcpus), 64-byte Cache-Line alignment, and NUMA-local memory allocation (`IMemoryArena`).
* **Kernel Bypass:** All network I/O utilizes DPDK/io_uring and RDMA (RoCE v2) to bypass the OS networking stack entirely.
* **Eventual SQL (CQRS):** The database (SQL) is never in the hot path; it is strictly a projection/audit store. Recovery is always **Snapshot + WAL Replay**.

---

## **2. Infrastructure & Hardware Abstraction Layer (HAL)**
*The layer that directly interfaces with the silicon, bypassing standard OS limitations.*

### **2.1 Networking & Transport (Kernel Bypass)**
* **Data Plane:** DPDK 26.03 for Linux and RIO for Windows. Network packets are written via Direct Memory Access (DMA) straight to pre-registered C# buffers.
* **Inter-Node Sync:** RDMA (RoCE v2) using Mellanox ConnectX-4+ or Intel E810 for microsecond cross-node state replication.
* **Sidecar Isolation (LD-INF-01):** Service meshes (mTLS, traffic shaping) are restricted to the Infrastructure Plane and never touch the execution hot-path.

### **2.2 Compute & NUMA Scheduling**
* **Thread Affinity:** The `AffinityScheduler` pins the Execution Thread, Network Poller, and WAL Writer to dedicated, isolated physical CPU cores.
* **NUMA Locality:** Memory allocated for a specific shard must reside on the physical RAM bank closest to the core executing that shard.

### **2.3 Memory Management (LD-PERF-01)**
* **`IMemoryArena`:** The engine provisions Large Pages (2MB/1GB) via `NativeMemory.AlignedAlloc`. 
* **Command Reset:** The arena offsets are reset after every command (O(1) allocation), guaranteeing zero fragmentation and zero GC pauses.

---

## **3. Transaction Processing Engine (The Hot Path)**
*The deterministic core where business logic executes.*

### **3.1 Shard Governance & Topology (LD-XX)**
* **Shard Catalog & Policy Engine:** A control plane that dynamically manages domain ownership, composite shards, and routing rules via declarative YAML/JSON configurations.
* **Composite Shards:** Multiple entities/domains can be co-located. Commands executing within a composite shard achieve **Single-Shard ACID semantics**, bypassing distributed Sagas.
* **Consistent Hashing:** Rendezvous hashing ring with dynamic shard addition/removal.

### **3.2 Execution Pipeline**
* **Command Pattern:** Applications submit intent-based commands. The `ShardExecutor` processes these sequentially.
* **Engine-Generated IDs (LD-ID-01):** Primary keys are generated by the engine *before* WAL append, ensuring replay determinism.
* **SIMD Vectorization:** Optional integration of `System.Numerics.Vector<T>` and AVX-512 for bulk data-parallel operations (e.g., risk scoring, columnar scans).

### **3.3 Native Multi-Tenancy (LD-MT-01 to 08)**
* **Engine-Level Isolation:** Every command, WAL record, and projection is strictly scoped by `TenantId`.
* **Shared vs. Dedicated Shards:** Tenants can be packed logically into Shared Shards or physically isolated onto Dedicated Shards based on Policy Engine rules.
* **Tenant-Aware Encryption & Quotas:** RBAC, throughput limits, and data encryption at rest are enforceable per tenant.

---

## **4. Write-Ahead Log (WAL) & Durability Engine**
*The single source of truth for the entire system.*

### **4.1 WAL Architecture**
* **Append-Only Sequential I/O:** Segmented log files utilizing `O_DIRECT` or `io_uring` to bypass the OS Page Cache.
* **Batching & Group Commit:** Multiple commands are coalesced into a single `fsync` to maximize NVMe throughput.
* **Zero-Copy Replication:** Replicating the WAL to follower nodes using `sendfile` or RDMA direct memory transfers.

### **4.2 Hybrid Retention & Tiered Storage**
* **Time/Key-Based Compaction:** Retaining only the latest state per AggregateId for rapid recovery.
* **Storage Tiers:** Hot (NVMe) -> Warm (SQL Projections) -> Cold (S3/Azure Blob).

### **4.3 Recovery Engine (LD-REC-01)**
* **Deterministic Replay:** Recovery relies *only* on the WAL and Snapshots. SQL is completely ignored.
* **Command Replay:** The engine replays serialized command envelopes through the `ShardExecutor`, not state mutations.

---

## **5. Read Fabric & Query Projections (LD-READ-01 & 02)**
*Decoupling reads to ensure the write-path remains uncompromised.*

### **5.1 Read Shards**
* **In-Memory Read Models:** High-volume queries hit dedicated Read Shards maintaining denormalized, pre-joined, columnar structures.
* **Query Filter Engine (LD-READ-DSL-02):** A shared engine utilizing compiled `Expression Trees` and cached delegates to perform zero-GC filtering, sorting, and grouping directly on `Span<T>`.

### **5.2 SQL Projections**
* Asynchronous event dispatchers push data to SQL Server/PostgreSQL using bulk TVP (Table-Valued Parameters) for historical analytics and audit reporting.

---

## **6. Extensibility & Orchestration (LD-FUNC-01 to 04)**
*Allowing complex workflows without poisoning the determinism of the core.*

### **6.1 Post-Commit Orchestration**
* Workflows and sagas operate strictly *after* transaction commit by consuming emitted Domain Events.
* **Strict Isolation:** Orchestrators run in separate processes/containers. They cannot access in-memory shard state or the WAL. They interact only by submitting new Commands to the Gateway.

### **6.2 Engine-Native DSL (LD-DSL-01)**
* An optional capability to define workflows via Expression Trees that compile into cached delegates. Executed inside a dedicated Orchestration Plane, free from I/O or randomness.

---

## **7. Cloud-Neutrality & Kubernetes Strategy (LD-K8S & LD-DEP)**
* **Infrastructure Plane Only:** Kubernetes is used for deployment, networking, and scaling. It is *prohibited* from participating in transaction ordering, WAL replication, or commit protocols.
* **Custom CRDs/Operators:** Shard lifecycle, leader promotion, draining, and cold restores are managed by bespoke Kubernetes Operators, not native K8s schedulers.

### **1. The "Brownfield" Read Migration: How much data do we load?**

If a developer migrates a 10-year-old application to VectorVolt, loading 10 years of data into the nanosecond `IMemoryArena` is both physically impossible and architecturally wrong. 

VectorVolt solves this using **LD-BOOT-01 (Read Fabric Bootstrap)** and **Tiered Storage**.

* **The YAML Configuration (Time-Windows):** In the topology YAML, the developer defines a "Hot Window." For example: `hot_retention: "30_days"`.
* **The Backfill Phase (LD-BOOT-01):** On initial boot, VectorVolt executes a "backfill" from the legacy database, loading *only* the last 30 days of data into the ultra-fast in-memory Read Shards. After reaching the current offset, it seamlessly switches to **WAL streaming** for new real-time updates.
* **Tiered Routing:**
    * **Hot Queries (e.g., "Show my recent orders"):** The engine answers instantly from the in-memory Read Fabric.
    * **Cold Queries (e.g., "Show my tax history from 2018"):** The engine routes this request transparently to the underlying "Warm" SQL projection or "Cold" Object Storage. 
* **The Result:** The developer doesn't change their app's logic. VectorVolt acts as a smart router, keeping the L1/L2 CPU caches uncluttered for the 1% of data that is accessed 99% of the time.

### **2. Hardware Crashes & Recovery (The "Mean Time to Recovery")**

When a server physically bursts into flames, you cannot rely on querying a slow SQL database to figure out what state the engine was in. This is governed by **Section 53 & 55: Recovery Engine (Locked)**.

* **Rule 1: No DB Reads During Recovery:** Recovery is **WAL-driven only**. The engine never queries SQL to rebuild its core state.
* **Rule 2: Snapshot + Log Replay:** To recover a crashed shard, the engine loads the latest binary Snapshot into the `MemoryArena`, then replays the WAL from the exact moment of that snapshot.
* **Recovery Speed:** Because the `ShardExecutor` is processing commands in memory without network/disk I/O bottlenecks during replay, it can reconstruct state at millions of operations per second. If your snapshot was 5 minutes old, VectorVolt rebuilds the exact state in a fraction of a second.
* **High Availability (Failover):** Using **Active-Passive or Active-Active log replication**, a secondary node (Follower) already has the replicated log. If the Leader crashes, the Follower takes over almost instantly by finishing the replay of the replicated log.

### **3. Cloud Neutrality & On-Premises Freedom**

You mandated this perfectly in **LD-DEP-01: Cloud-Neutral Mandate**. The engine must run unchanged on AWS, Azure, and On-Prem. 

How do we achieve hardware-level Mechanical Sympathy (like RDMA and CPU pinning) while remaining hardware-agnostic? We use the **Hardware Abstraction Layer (HAL) Platform Adapters**.

* **On-Premises (The Gold Standard):** The developer configures the engine to bind directly to a Mellanox ConnectX-6 NIC and physical Xeon Cores. They get absolute maximum performance.
* **AWS (Cloud Adapter):** AWS doesn't give you direct physical NICs, but they give you **EFA (Elastic Fabric Adapter)**. VectorVolt's AWS adapter translates our RDMA commands into EFA commands.
* **Azure (Cloud Adapter):** Azure offers **HBv3 virtual machines with native InfiniBand**. VectorVolt's Azure adapter leverages this for direct memory-to-memory transfers between VMs.
* **The Guarantee:** There is zero cloud-vendor lock-in regarding execution, durability, governance, or control-plane semantics. Storage, networking, and node affinity are entirely abstracted via these platform adapters.
